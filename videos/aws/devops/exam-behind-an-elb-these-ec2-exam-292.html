The correct solutions are: configure your instances to rotate and upload logs to Amazon S3 and use AWS Data Pipeline to transfer logs from S3 to Redshift. Here’s why:

  • Storing logs in Amazon S3 is reliable and durable, which means your log files are safely kept even if instances terminate. Using a scheduled script ensures logs are pushed regularly and not lost during scaling events.
  • Transferring logs from S3 into Redshift using Data Pipeline enables future analysis and allows the staff to run SQL queries against the data for reporting.

Why not the others?

  • Set up scheduled jobs ... into Amazon Glacier: Though Glacier is durable and cost-effective for archiving, it is not suitable for logs that need ongoing or interactive analysis. Retrieving data from Glacier can also take hours, making it impractical here.
  • Use AWS Data Pipeline ... into Amazon SQS: SQS is a queuing service, not designed for log storage or reporting. Moving data into SQS is not suitable for long-term analysis or storage.

Tip: For log storage and future querying, always use a durable, query-friendly service like S3 and Redshift. Glacier is for deep archive, and SQS is for ephemeral messaging.
