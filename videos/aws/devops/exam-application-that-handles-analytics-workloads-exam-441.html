The correct answer is: Leverage roles that permit federated web identity users to assume a role, granting temporary credentials that allow access to the Redshift table.

This method uses AWS Identity and Access Management (IAM) roles in combination with web identity federation (e.g., Amazon Cognito, Facebook, Google, or other supported identity providers). The application can request temporary, limited-privilege credentials. This approach reduces the risk associated with long-term credentials, supports best security practices (like least privilege and credential rotation), and is tailor-made for mobile and web applications where user access is dynamic and needs tight security controls.

Let's discuss why the others are incorrect:

  • Set up an HSM client certificate for Redshift and use this certificate for authentication. - Redshift does not support external client certificates for authentication via Hardware Security Modules (HSMs). This option does not correctly address Redshift's security model and is not viable.
  • Create a Redshift read-only policy in IAM and include the static credentials in the application code. - Embedding long-term IAM credentials within application code is a significant security vulnerability. If the application is ever decompiled or exposed, these credentials could be stolen, leading to unauthorized access and potential data breaches.
  • Provision an IAM user, generate encryption keys, and configure a policy for read-only Redshift access. Embed these keys within the app. - Similar to the previous option, embedding encryption keys or access credentials within the application poses a high security risk. Keys can be extracted and misused, and managing rotation and revocation becomes very challenging.

Tip: Always use temporary credentials and identity federation when building mobile or web apps that interact with AWS, to avoid hard-coding credentials and improve overall security.
