The correct answer is the option where you define a CloudWatch Event rule to detect ECS task state changes to 'STOPPED', using a Lambda target for Slack and SNS for email notifications. This approach is a best practice for ECS task status monitoring because CloudWatch Events provide native integration with ECS and deliver real-time, event-driven notifications without requiring log monitoring or parsing.

Why other options are incorrect:

  • Configure ECS cluster hosts to send logs from /var/log/ecs/ to CloudWatch Logs. Then, create a Metric Filter looking for 'STOPPED', and set up an Alarm to invoke a Lambda function that sends the alerts to Slack and the email group. – This relies on parsing logs to detect stopped tasks, which is indirect, more complex, and less reliable since log formats can change and there could be delays in parsing.
  • Build a CloudWatch Event rule for 'ECS Container Instance State Change' where desired status is 'STOPPED', and make a Lambda function notify both Slack and the relevant email list as its single target. – This option monitors the container instance lifecycle, not ECS task lifecycle, so it won't catch when an individual task is stopped. It misses the required granularity.
  • Send /var/log/docker/ logs from ECS cluster instances to CloudWatch Logs, and create a Metric Filter for 'STOPPED'. On Alarm, trigger an SNS topic and have a Lambda function subscribed to send updates to the Slack channel and email list. – Like the previous log-based method, this is convoluted and can result in missed or late alerts, since it's not specifically tuned to ECS task state events.

Tips: Always consider monitoring actual events (CloudWatch Events/EventBridge) for critical state changes rather than relying on log analysis. This is more efficient, timely, and less prone to errors or format drift. Leveraging multiple targets in the event rule (such as Lambda for Slack and SNS for emails) provides separation of concerns and easier maintainability.
