Insert a DeletionPolicy set to 'Snapshot' for the RDS resource in the CloudFormation template ensures that when the stack is updated and the RDS resource is replaced—such as when enabling encryption, which requires a new database instance—a snapshot of the existing (unencrypted) database is automatically taken by CloudFormation before deletion. Include the DBSnapshotIdentifier property referencing the most recent DB snapshot ID allows CloudFormation to restore the new (encrypted) database instance from the specified snapshot, preserving data during the resource replacement.

The other choices are either incomplete or do not satisfy the requirements for automated, stack-managed data protection: Disable any applications or services accessing the current DB instance, then take a manual database snapshot is good practice but not integrated into the CloudFormation stack's automation. Apply a Stack Policy on the CloudFormation stack to protect the DB resource from accidental deletion prevents resource deletion but does not facilitate data restoration or replacement with encryption. Validate that automated snapshots are working and keep a record of the latest snapshot's ARN is good for monitoring, but it does not ensure that the replacement DB is restored with the required encryption via CloudFormation automation.

Tip: When enabling encryption for RDS using CloudFormation on an existing database, you must create a new instance from an encrypted snapshot and automate recovery within the stack to avoid manual steps and potential data loss.
