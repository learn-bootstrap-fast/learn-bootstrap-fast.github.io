The most probable cause is that you reached the default AWS Lambda concurrency limit because a request for higher concurrent executions was not submitted. When demand suddenly escalates, such as to 3000 requests per second, and you haven't increased your Lambda's concurrency quota, AWS will throttle new invocations, resulting in elevated failure rates. This fits with why DynamoDB's consumed capacity and primary key design are not the source.

You did not request an increase for the maximum concurrent executions allowed for Lambda functions.: This is correct. By default, AWS imposes a concurrency limit (e.g., 1,000 per account per region), which you must proactively increase for high-traffic workloads. Until you do, the platform will reject requests above this threshold, impacting system reliability during spikes.

API Gateway was applying throttling to incoming requests.: This is unlikely. While API Gateway can throttle, it would limit ALL incoming requests and you’d typically see errors at the API Gateway level, not Lambda invocation errors. Your usage profile points to Lambda being the bottleneck, not the gateway.

There was a bottleneck in API Gateway while serializing and deserializing requests.: API Gateway is designed to efficiently handle request (de)serialization at these volumes. This would be rare without a more complex transformation pipeline, and you would see a throughput bottleneck at API Gateway rather than Lambda.

Semaphore lock contention was causing issues in the DynamoDB table.: The scenario states that DynamoDB’s throughput is under 50%, and the primary key structure is not at fault. Semaphore lock contention is thus very unlikely, as is any DynamoDB performance issue.

Tip: Always monitor the Lambda concurrency metrics and request a soft-limit (quota) increase in advance when scaling up serverless workloads.
