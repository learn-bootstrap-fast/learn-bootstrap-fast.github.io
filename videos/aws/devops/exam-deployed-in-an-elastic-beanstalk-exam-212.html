The Immutable deployment strategy in Elastic Beanstalk is specifically designed to ensure smooth upgrades and fast rollbacks without causing downtime or running two entire environments. With immutable deployments, Elastic Beanstalk provisions a new set of instances with the updated application version. These new instances must pass health checks before traffic is routed to them. If the new deployment is unhealthy, it can easily be terminated, reverting back to the original group of instances.

The other options are not optimal for this scenario:

  • Choose a Rolling with additional batch deployment strategy to launch extra instances for each update. – While this method does add extra instances temporarily and reduces downtime, it can still serve partial traffic to older or unhealthy versions during deployment, which does not fully mitigate risk of user disruption.
  • Implement a Rolling deployment by launching new app versions on new EC2 instances and then connecting them to the existing load balancer. – Regular Rolling updates replace instances in batches, which can lead to periods where some users are routed to the new, untested version before health checks complete. Problems with the new version could affect some users during deployment.
  • Utilize a Blue/Green deployment by swapping Elastic Beanstalk environment URLs. – This option does offer reliable rollbacks and no downtime, but it requires maintaining two separate environments momentarily, which the question states should be avoided.

Tip: Immutable deployments offer the safest and most automated way to roll out new versions without risking downtime or exposure to unhealthy releases, and do not require the overhead of a full duplicate environment like Blue/Green deployments.
