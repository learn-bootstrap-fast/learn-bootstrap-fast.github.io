Lambda@Edge functions can be triggered at four primary CloudFront lifecycle events: Viewer request, Origin request, Origin response, and Viewer response. These trigger points allow developers to execute code at the edge, enabling dynamic selection of A/B test content without changing the web application's core codebase.

\n

Why the correct choices are right:

\n
    \n
  • Viewer request: Occurs when CloudFront receives a request from an end user—ideal for handling content selection before the cache or origin is consulted.
    • \n
  • Origin request: Triggered when CloudFront forwards a request to your origin (web server, etc.), useful when modifying headers or selecting content after cache miss.
    • \n
  • Origin response: Initiated when CloudFront receives a response from the origin, which enables content modification right before it's cached or sent back to the user.
    • \n
  • Viewer response: Happens just as CloudFront sends a response to the user, allowing final alterations or header manipulations before content delivery.
    • \n
\n

CloudFront cache is not a supported Lambda@Edge event. It does not represent a trigger point for Lambda execution; it's a storage mechanism where files are cached, but no code execution occurs directly at this phase.

\n

Tip: To perform advanced content personalization or A/B testing at the edge, use Lambda@Edge at the appropriate event hook that matches the logic you wish to apply. Understanding where these hooks fit into the CloudFront request/response cycle is crucial for optimizing performance and capability.
