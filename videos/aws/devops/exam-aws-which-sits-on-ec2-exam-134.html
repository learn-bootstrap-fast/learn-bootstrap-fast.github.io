The most effective way to diagnose slow response times for an application behind an Elastic Load Balancer (ELB) is to review the Elastic Load Balancer access logs. These logs provide detailed information about request processing times, backend latency, client and target IPs, response codes, and more. By investigating these logs, you can pinpoint whether delays are from the load balancer's processing or the backend servers themselves, and identify patterns correlated with the new feature.

The option to log all API activities with CloudTrail and comb through the logs to discover clues is not directly helpful for performance issues since CloudTrail is better for tracking AWS API calls for security, auditing, and compliance rather than pinpointing response delays for web requests.

While track CPU usage over time with CloudWatch to spot any CPU spikes correlating with issues might help detect if there are resource bottlenecks, it does not necessarily point to whether the source of latency lies at the ELB or another part of your app—plus, not all performance problems are caused by CPU exhaustion.

Setting up custom CloudWatch metrics tailored to critical application features can provide insight for future incidents, but won't immediately help you diagnose the current problem unless those metrics were already in place before the issue began.

Tip: Always enable ELB access logs in production environments as a best practice to help with swift diagnostics when problems arise.
