The correct answers are: Utilize an in-memory caching solution such as ElastiCache with Multi-AZ capabilities and Set up an RDS MySQL read replica in every availability zone.

Here's why:

  • Utilize an in-memory caching solution such as ElastiCache with Multi-AZ capabilities: Using a caching layer like ElastiCache can significantly decrease the volume of read requests to the RDS instance. Frequently accessed data can be stored and served directly from memory, offering much faster read performance, reducing database contention, and improving scalability. Since the site is tolerant of eventual consistency, the caching strategy aligns well with the application's needs.
  • Set up an RDS MySQL read replica in every availability zone: Adding read replicas distributes read traffic, easing the load on the primary instance and providing high availability. Read replicas can be used to serve read-heavy workloads, which directly addresses the read contention observed.

Why the other choices are less suitable:

  • Upgrade the RDS MySQL instance size and enable provisioned IOPS: While upgrading the instance and provisioning more IOPS may help with performance bottlenecks, this is primarily effective for write-heavy or I/O-constrained workloads. Since the issue is specifically with read contention, simply increasing hardware resources doesn't address the underlying scalability and distribution challenges.
  • Partition the database workload by implementing sharding across multiple RDS MySQL instances: Sharding can certainly increase scalability, but it adds significant application and operational complexity. The scenario can be addressed efficiently with caching and read replicas, so sharding is not the most appropriate initial remedy.

Tips: For read-heavy workloads, always consider read replicas and caching before embarking on complex redesigns like sharding. Leverage AWS managed solutions like ElastiCache and RDS read replicas to scale efficiently and effortlessly.
Remember: Caching and read replicas are powerful approaches, especially when your application accepts eventual consistency!
