The correct answer is Identify the compute bottleneck, use that as the scaling metric, and set CloudWatch alarm thresholds to values that trigger scaling only when performance starts to degrade. This approach ensures that scaling actions are based on the specific metric that accurately reflects system performance bottlenecks rather than arbitrary metrics such as CPU utilization alone, which may not fully capture the workload nature. Setting thresholds aligned to when user-facing latency or performance issues first arise provides responsive yet stable scaling behavior.

Here's why the other options are less effective:

  • Increase the Auto Scaling cooldown period to ensure additional instances have more startup time before new scaling actions occur. — While cooldowns prevent repeated scale-outs before new instances are ready, they don’t directly address the root problem: scaling decisions based on inappropriate or overly sensitive metrics, which still causes over-provisioning or sluggish scale-down.
  • Switch to larger EC2 instance types so fewer are needed and the Auto Scaling Group doesn't scale out as frequently. — This can sometimes reduce the total number of instances, but the fundamental issue is still there if scaling is triggered for the wrong reasons; you might just have more powerful idle resources wasting cost.
  • Raise the CloudWatch alarm thresholds on your auto scaling group to require much higher demand before scaling up. — Raising thresholds only delays scaling action, which could lead to slow responses during actual spikes, and only masks rather than solves the underlying metric-related problems.

Tip: Choosing metrics like application response time, request queue length, or specific resource limitations helps ensure the Auto Scaling Group reacts proportionally to real load, reducing the risk of unnecessary over-scaling and cost.
