The best way to maintain compatibility for version1 consumers is to use a mapping template in the Integration Response of the version1 API to remove the additional fields from the Lambda response, ensuring the format stays consistent with what clients expect. This approach enables you to process the backend response before it is sent to the client—removing any unwanted or new fields introduced by Lambda code changes.

The option Insert a mapping template in the Method Response of the version1 API so that the extra data is stripped out, maintaining previous output behavior is incorrect because method response is not responsible for transforming or filtering the backend data; it mainly defines models and status codes.

The choice Configure a Header Mapping within the Integration Response of version1 API to remove any new data present in the backend reply is misleading because header mapping is for HTTP headers—not the body of the response which contains the new fields.

The suggestion Set up a mapping in the Integration Request of version1 API so the Lambda backend omits the additional data when producing the response is also not accurate, as integration request mapping is used to transform the incoming request, not the Lambda’s outgoing response.

Tip: Use an integration response mapping template when you need to modify or filter the response payload from the backend before it is returned to the client—especially when managing API version compatibility.
