The most effective solution is to Integrate an Amazon SQS queue between your web layer and DynamoDB to help buffer heavy bursts of requests during peak times. By leveraging SQS, your application can decouple the influx of requests from direct interaction with DynamoDB, smoothing out spikes during times like the 9:00AM user rush. This helps prevent the DynamoDB table's provisioned capacity from being overwhelmed, thereby minimizing throttling and improving user experience.

The option Switch your Auto Scaling group to use Amazon C3 instances to address potential compute bottlenecks at the application layer is unrelated because the bottleneck resides in the database backend, not the levels of compute capacity.

While Move to an ElastiCache Memcached cluster in one Availability Zone to cache frequently accessed data in front of the web tier can help for cacheable data, depending solely on a single AZ risks availability, and caching alone doesn’t solve all DynamoDB throughput and partitioning issues.

Simply Increase the Write Capacity Units of your DynamoDB table, as write throttling may occur when users access the site may not be cost-effective, especially if the traffic spike is temporary; you could still have hot partitions, so it’s not the most efficient first step.

Lastly, Migrate the data to a new DynamoDB table with a more evenly distributed partition key, and adjust your application accordingly is a considerable architecture change—while it's best practice to design a good distribution up front, it's complex to execute just to solve sporadic traffic spikes.

  • Tip: For web applications experiencing short, predictable bursts of traffic, message queues like SQS can buffer and smooth workload to backend systems without the need for immediate and substantial scaling changes.
