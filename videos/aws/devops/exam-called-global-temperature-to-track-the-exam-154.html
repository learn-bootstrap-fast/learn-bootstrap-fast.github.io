The best solution is to add a Global Secondary Index (GSI) where CityId is the partition key and HighestTemperature is the sort key. GSIs provide the flexibility to query data with entirely new key structures, independent of the table’s primary key. This allows your queries to efficiently fetch all temperature records for a city, sorted or filtered by their recorded highest temperature without restructuring the base table or migrating data.

Here’s why the other options are not correct:

  • Revise the current table to have CityId as the partition key and HighestTemperature as the sort key. — Modifying the primary key for an existing DynamoDB table is not feasible; you’d have to destroy and recreate the table, resulting in downtime and potential data loss.
  • Introduce a Local Secondary Index using CityId for the partition key and HighestTemperature for the sort key. — Local Secondary Indexes (LSIs) require the same partition key as the base table, which in this case is CountryId. Since CityId is different, an LSI cannot be used here.
  • Create both a Global Secondary Index with CityId as the partition key, and a separate Global Secondary Index with HighestTemperature as the partition key. This is required because the primary index only employs a single-partition key, so secondary indexes are restricted to single-partition keys as well. — This suggestion is not only inaccurate but also inefficient. GSIs can have both a partition key and a sort key. Furthermore, you only need one suitable GSI to cover your query requirement. The statement about GSIs being limited to a single attribute as a partition key is incorrect.

Tip: Use Global Secondary Indexes to support new and diverse query patterns in DynamoDB, particularly when querying relationships and attributes not included in the table’s primary key.
