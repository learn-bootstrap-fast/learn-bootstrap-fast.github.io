The third option is the best security practice: storing sensitive data such as credentials in the AWS Systems Manager Parameter Store and referencing them via the parameter-store mapping in the env section of buildspec.yml. This avoids exposing secrets in plaintext within the file and leverages AWS's secure parameter management with encryption-at-rest and fine-grained access control.

Here's why the other options are not recommended:
\"Store the buildspec.yml file in AWS CodeCommit instead of GitHub, relying on IAM policies in CodeCommit for enhanced security.\" – While CodeCommit offers IAM integration, it does not specifically protect secrets hardcoded in buildspec.yml. The file would still contain sensitive data.
\"Save the credentials in an encrypted S3 bucket using SSE-S3, and update the buildspec.yml file to retrieve and use the encrypted file from that S3 bucket.\" – Although S3 encryption adds a basic layer of security, managing secrets this way is less integrated than using the Parameter Store or Secrets Manager and can be harder to manage securely at scale.
\"Apply a restrictive IAM policy in AWS CodeBuild to ensure only a few users have access to the buildspec.yml file.\" – While IAM can control file access, this does not prevent those with access from viewing plaintext secrets in the buildspec file.

Tip: Always use a secret management service such as Parameter Store or Secrets Manager to inject sensitive values at runtime rather than storing secrets in code or config files. This minimizes the risk of unintentional exposure.
