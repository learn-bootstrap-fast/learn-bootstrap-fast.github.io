The correct answers are: The main database instance is unintentionally deleted and There is a failure of RDS hardware on the primary instance.

A Read Replica keeps an asynchronous copy of the primary database. If the original database is lost—such as in the case where the main database instance is unintentionally deleted—or if there is a failure of RDS hardware on the primary instance, the Read Replica can be promoted to replace the source as it contains all data replicated up to the most recent point.

The other choices are not suitable recovery scenarios:

  • A bug in the application has accidentally erased some records from the primary database. – Deletions made at the source are also replicated to the replica, so deleted data cannot be recovered from the Read Replica.
  • The AWS account containing the databases has been compromised. – If the AWS account itself is compromised, all resources within that account are at risk, including the Read Replica, making it unavailable as a recovery option.
  • A regional outage impacts both ap-southeast-1 and ap-southeast-2 at the same time. – Since both the source and the replica are affected, it would not be possible to recover data from the Read Replica.

Tips: Use Read Replicas across regions for high availability and disaster recovery only if the disaster is localized to one region or the source instance itself. Remember, logical errors (such as unintentional deletions or bad application logic) are always replicated, so snapshots or backups are better suited to protect against such issues.
