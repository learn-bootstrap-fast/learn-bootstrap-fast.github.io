The second option is the most effective and non-disruptive method to update the instance type in an Auto Scaling Group (ASG). By creating a new launch configuration with the updated instance type, associating it with the existing ASG, and then incrementally increasing the desired capacity, new instances with the correct type will be provisioned. After verifying that these units are healthy and properly serving traffic, you can decrease the desired capacity back to its original value, causing ASG to terminate the outdated instances. This process ensures continuous availability and zero downtime.

Why not the others?

  • 'Deploy the application to Elastic Beanstalk, specifying the updated instance type.'—This introduces unnecessary complexity since the current solution already uses an ASG. Migrating to Elastic Beanstalk is not required just to change the instance type.
  • 'Terminate the previous Auto Scaling Group and provision a new one through CloudFormation that uses the updated instance type.'—Deleting the original ASG can interrupt service, especially if traffic isn't cut over cleanly, resulting in a potential service impact.
  • 'Provision new EC2 instances with the intended instance type and manually add them to the current Auto Scaling Group.'—EC2 instances cannot be manually attached to an ASG; new instances must be launched by the ASG itself per the settings in its launch configuration or template.

Tip: Always use updated launch configurations or launch templates for instance type changes. Increase desired capacity for rolling replacements to ensure zero downtime. This technique is frequently tested in AWS Solution Architect exams.
