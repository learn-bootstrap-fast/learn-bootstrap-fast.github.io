The event pattern that will successfully notify you when a CodeDeploy deployment either fails or succeeds is { \"source\": [ \"aws.codedeploy\" ], \"detail-type\": [ \"CodeDeploy Deployment State-change Notification\" ], \"detail\": { \"state\": [ \"FAILURE\", \"SUCCESS\" ] } }.

Explanation and Tips:
This pattern is correct because it targets deployment state changes (not instance-level changes), and it filters only the FAILURE and SUCCESS states, which are relevant for complete deployment events, not per-instance transitions.

Why others are incorrect:

  • { \"source\": [ \"aws.codedeploy\" ], \"detail-type\": [ \"CodeDeploy Instance State-change Notification\" ], \"detail\": { \"state\": [ \"FAILURE\", \"SUCCESS\", \"READY\", \"START\" ] } }: This pattern matches individual instance changes within a deployment, producing excessive noise and not indicating full deployment outcomes.
  • { \"source\": [ \"aws.codedeploy\" ], \"detail-type\": [ \"AWS API Call via CloudTrail\" ], \"detail\": { \"state\": [ \"FAILURE\", \"SUCCESS\" ] } }: 'AWS API Call via CloudTrail' is an incorrect detail-type for CodeDeploy deployment status; CloudTrail logs API events, not deployment results.
  • { \"source\": [ \"aws.codedeploy\" ], \"detail-type\": [ \"CodeDeploy Instance State-change Notification\" ], \"detail\": { \"state\": [ \"FAILURE\", \"START\" ] } }: This option also focuses on instance-level changes and misses the SUCCESS state that is critical for deployment completions. It will not capture all necessary deployment outcomes.

When configuring event patterns for deployment notifications, always use detail-type CodeDeploy Deployment State-change Notification and select only the states relevant for full deployments (typically FAILURE and SUCCESS). Instance-level notifications lead to redundant or irrelevant alerts, and improper detail-type prevents the rule from triggering on deployment events.
