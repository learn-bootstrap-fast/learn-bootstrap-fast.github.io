The best solution is to use a Custom resource in your CloudFormation template and specify the Lambda function's ARN in the ServiceToken property. This way, CloudFormation will invoke your Lambda function during stack operations, and the Lambda can return the up-to-date AMI ID dynamically. This approach is fully automated and ensures your stacks always deploy with the correct AMI, without manual updates or intervention.

Why other options are not ideal:

  • Call the Lambda function by running a shell script before the stack creation or update, and then manually supply the returned AMI ID to CloudFormation: This requires manual scripting and does not scale well—it isn't automated and increases the risk of using outdated AMI IDs.
  • Set the Lambda function's name as the value for the custom resource's RequestId property in the CloudFormation template.: This misunderstands how the ServiceToken property works; the RequestId is not used to associate a Lambda function.
  • Input the AMI ID as a parameter when launching the CloudFormation stack.: You still have to manually retrieve and enter the AMI ID, which doesn't solve the core issue of automation or currency.
  • Run the Lambda manually, store the result in Parameter Store, and revise your template to fetch the AMI ID from there.: This approach introduces another manual process and adds complexity with possible data staleness if the Parameter Store value is not frequently updated.

Tip: Leveraging custom resources is the AWS-recommended way when you need dynamic values not natively supported by CloudFormation's intrinsic functions.
