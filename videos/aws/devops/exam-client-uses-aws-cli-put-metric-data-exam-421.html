The most cost-effective solution is to Consolidate the data points before publishing and use a single put-metric-data call with the --statistic-values parameter to submit a statistics set. By aggregating the data in your application over 1-minute intervals and then sending that set as a statistics set, you can minimize API usage while still ensuring all relevant data (min, max, sum, and sample count) is available for CloudWatch analytics and alarms. This method keeps your metrics granularity and detail, with much fewer API calls.

The following explains why the other options are not ideal:

  • Send multiple numerical values together in one put-metric-data call using a syntax like --value 2,5,2,7,9. – The --value parameter does not accept multiple values in one call; a single metric value per call is required unless using statistics sets with --statistic-values.
  • No changes are needed, since CloudWatch costs are determined by the number of metrics, not the number of put-metric-data API requests. – This is inaccurate; while metric storage is a major cost factor, excessive API requests can also incur additional costs and may hit service limits. Reducing request count is best practice for efficiency and cost savings.
  • Aggregate the application's data and request the metric statistics in the application, eliminating the need to use put-metric-data API calls. – Applications still need to publish data to CloudWatch to monitor and trigger alarms. Aggregating in the application and skipping metric publishing would make your metrics unavailable in CloudWatch, which is typically not an acceptable solution.

Tip: Use statistics sets when sending aggregated data to CloudWatch to combine resolution, accuracy, and cost efficiency.
