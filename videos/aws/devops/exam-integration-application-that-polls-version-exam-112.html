The best way to optimize for both speed and cost is to run as many early-stage checks as possible—such as syntax and build verification—on the existing continuous integration (CI) system, rather than launching additional Amazon EC2 instances. The \"Carry out syntax and build validation within the continuous integration (CI) system prior to spinning up new Amazon EC2 instances for unit and integration tests.\" option is correct because it ensures that only the code that passes basic checks results in launching new instances for more resource-intensive tests.

The other options don't achieve this:

  • \"Use AWS OpsWorks in your CI system to perform all syntax, unit, integration, and build tests on the existing infrastructure.\" is incorrect since using OpsWorks to do everything in one place may limit your ability to parallelize test runs and won't leverage cheap/high-performance scaling of EC2 launches.
  • \"Use the CI system to only perform syntax validation before triggering an AWS Data Pipeline that orchestrates unit, integration, and build tests.\" is misleading because AWS Data Pipeline isn't designed for running application tests—it's mainly for ETL workflows and data processing, not CI pipelines.
  • \"Have the CI system check syntax only, before launching an Amazon EC2 instance to run all types of tests including build, unit, and integration.\" is suboptimal; you want to filter as much as possible (such as failing builds) before incurring EC2 instance costs. Running only a syntax check on CI, and pushing all other tests to EC2, might waste money on tests that could have been filtered out sooner.

Tip: Always perform lightweight validations early in your pipeline using existing resources. Trigger extra infrastructure for heavier tests only after code has passed these initial stages to maximize parallelism and minimize unnecessary resource usage and cost.
