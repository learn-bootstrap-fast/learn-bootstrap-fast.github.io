The correct approach is to Adjust the detail-type field in the rule to be \"CodeDeploy Deployment State-change Notification\". This ensures that the CloudWatch Event rule (now called Amazon EventBridge) is triggered only when specific CodeDeploy deployment events, such as state changes, are emitted. Within the event details, you can then filter for failed deployments, which makes the notification flow efficient and targeted for your requirement.

The option Remove the detail-type from the EventBridge rule to capture all CodeDeploy events, then implement the logic in the Lambda function to identify deployment failures and dispatch notifications would lead to the Lambda function being invoked for every single CodeDeploy event, not just deployment failures. This increases unnecessary invocations and can complicate your Lambda function’s logic.

Choosing Set up an SNS topic as the target for the CloudWatch Event rule instead of Lambda, and subscribe an HTTP endpoint to this topic is not relevant to filtering deployment failures. While SNS can be used for notification, it doesn’t address the requirement to filter only failed deployments specifically within the rule.

Finally, Ensure that the Lambda function is exposed via API Gateway so it can accept API requests from events.amazonaws.com is incorrect because Lambda can be directly invoked by EventBridge/CloudWatch Events without needing API Gateway. API Gateway is necessary only when integrating with external HTTP requests, which is not the case here.

Tip: Always try to filter as much as possible within the event rule itself to avoid extra compute and logic burden on downstream services like Lambda.
