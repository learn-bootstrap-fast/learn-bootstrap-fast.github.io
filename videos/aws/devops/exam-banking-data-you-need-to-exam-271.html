\"Configure DynamoDB Streams to forward all changes to AWS Lambda, where sensitive data is redacted before forwarding the sanitized changes to CloudWatch Logs\" is correct. This solution leverages DynamoDB Streams to capture every data mutation in real time. AWS Lambda processes each stream record, ensuring every change is noted and sensitive details can be scrubbed before delivering logs to CloudWatch Logs for durable, searchable audit storage. This workflow is scalable, serverless, minimizes data loss risks, and ensures redaction is performed consistently.

Let's break down the other options:

  • \"Prior to saving data in DynamoDB, write a sanitized record (excluding sensitive content) to disk on the application server. Regularly rotate these files to S3 for long-term audit storage.\" – This approach could miss updates if the application server fails before writing both files, introduces operational overhead, is not scalable, and may lead to inconsistent logging.
  • \"Set up DynamoDB Streams to periodically send updates to an EC2 instance's local drive. Remove confidential information before storing. Consolidate and migrate these logs to S3 at intervals.\" – This adds unnecessary complexity by using an EC2 instance and local storage, creates risks of data loss if the instance fails, and complicates durability.
  • \"Before committing data to DynamoDB, log a redacted version to local disk on the app server. Pipe these logs into CloudWatch Logs periodically for audit purposes.\" – Similar to the previous disk-based approach, this is not fail-safe: a server crash could lose audit entries and increase operational complexity. It also does not operate in real time.

Tips: Use DynamoDB Streams with Lambda for real-time, serverless change detection with built-in durability. Always sanitize sensitive information before logging and prefer managed solutions (like CloudWatch Logs) for storing critical audit trails.
