The preferred approach is to implement a CloudFormation Custom Resource Type with your own create, update, and delete handlers, via Lambda or SNS. This lets you seamlessly extend CloudFormation’s capabilities by invoking Lambda functions or integrating with custom providers when unsupported resources are needed.

Here's why the other options aren’t ideal:

  • Request the addition of your required resource type by submitting a ticket to the AWS Forums, where AWS engineers can provide tools through AWS Labs on GitHub... – This is not an established or reliable process for extending CloudFormation functionality, and there’s no guaranteed response or fulfillment time.
  • Build a CloudFormation Custom Resource Template by configuring automated API calls for necessary actions... – Custom resources are defined by implementing create/update/delete logic, typically using Lambda or SNS, not by proxying through the SDK or CLI natively within a template.
  • Adopt third-party configuration management tools such as Chef, Puppet, or Ansible to write Heat templates... – Heat templates are specific to OpenStack and do not apply to AWS. Chef, Puppet, and Ansible are alternatives to CloudFormation but do not extend its resource types.
This approach allows your CloudFormation stacks to remain declarative, consistent, and repeatable, even as you handle resources outside the built-in support— a useful solution for many real-world AWS scenarios.
