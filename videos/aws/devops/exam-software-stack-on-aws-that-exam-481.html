Bake an AMI containing the latest application code, and configure your Auto Scaling Launch Configuration to use this AMI for new instance launches is the preferred practice. By preparing an Amazon Machine Image (AMI) with your application stack and all necessary dependencies included, instance initialization is fast and consistent. This enables the Auto Scaling Group to respond very quickly to increases in demand since new instances require minimal setup—they boot with the latest code and are ready to serve traffic nearly instantly. This approach reduces the risk of deployment errors and ensures all instances are identical.

The other options each introduce potential delays or risks:

  • SSH into each new EC2 instance... is impractical and non-scalable for automated environments, especially under rapid scaling where manual intervention is infeasible.
  • Prepare a Dockerfile... and execute it on launch adds extra boot time since the Docker images still have to be built or downloaded when each instance starts, slowing the launch process compared to an already-baked AMI.
  • Implement UserData scripts to always fetch the latest code means every new instance will have to pull from a remote repository at boot. This can fail, introduce inconsistencies (if the remote codebase changes during scaling activity), and also makes instance startup slower.

Tip: AMI baking—often through automation pipelines—ensures reliability, speed, and repeatability. For ultra-fast scaling and minimal run-time configuration issues, always try to use golden AMIs pre-baked with all dependencies and application code.
