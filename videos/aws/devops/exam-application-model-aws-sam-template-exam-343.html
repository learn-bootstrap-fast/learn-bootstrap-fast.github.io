The correct answer is During the deployment, 10% of user traffic is rerouted to the new Lambda version immediately, and after five minutes, the leftover 90% is redirected to the new version.

This reflects how the Canary10Percent5Minutes deployment configuration works in AWS CodeDeploy. It gradually shifts a small portion of traffic (10%) to the new Lambda version, waits for five minutes to monitor performance and errors, then redirects the remaining traffic. This helps prevent full-scale impact in case of issues with the new version.

The other statements are incorrect for the following reasons:

  • If a health check alarm like AliasErrorMetricAlarm triggers, CodeDeploy does not roll back the deployment. – This is incorrect. If an alarm configured for rollback (for example, AliasErrorMetricAlarm) goes into the Alarm state during deployment, CodeDeploy automatically rolls back to the previous version to maintain function availability.
  • A failed PreTrafficLambdaForValidation hook does not cause the deployment to roll back. – This statement is false. If the PreTrafficLambdaForValidation hook fails, CodeDeploy halts the deployment and can roll back, because the pre-traffic validation step is critical to verifying the new version before routing traffic.
  • If the PostTrafficLambdaForValidation lifecycle event fails, CodeDeploy does not roll back the deployment. – Similarly, if PostTrafficLambdaForValidation fails, CodeDeploy will typically roll back the deployment according to the deployment configuration for the service. Both Pre- and PostTraffic hooks are designed to ensure the deployment is safe.

Tip: Use the appropriate Canary or Linear deployment configuration for safe production releases, and always pay attention to the lifecycle hooks and rollback alarms to ensure reliable deployments.
