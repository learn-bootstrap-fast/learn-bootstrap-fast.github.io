The correct solution is to select the 'Configuration changes' trigger type with the scope limited to 'EC2: SecurityGroup'. This ensures the Config rule runs evaluations whenever there is a configuration modification specifically to an EC2 security group, thus aligning evaluations directly with relevant resource changes.

The other responses are less suitable:

  • 'Set the trigger type to Periodic with a 1-hour frequency and limit the scope to EC2: SecurityGroup resources.' - This option only evaluates the rule on a scheduled basis rather than immediately after configuration changes, which could result in delayed detection of issues.
  • 'Choose Configuration changes as the trigger type and set the scope to include the tag assigned to the security groups; ensure every security group (existing and new) has this tag.' - This introduces unnecessary dependency on a specific tag and management overhead, making it easy to miss security groups if they're not properly tagged. The most direct and reliable scope is targeting the resource type itself.
  • 'In the Config rule trigger, pick Configuration changes and set the scope to All changes for all EC2 resource types.' - Scoping to all EC2 changes is inefficient and could result in unnecessary rule evaluations for irrelevant resources, creating unnecessary noise.

Tip: Always scope your Config triggers as narrowly as possible for the resource and change type relevant to your policy. This improves performance, reduces cost, and minimizes extraneous compliance alerts.
