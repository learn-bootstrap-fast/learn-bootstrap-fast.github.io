The most cost-effective solution is to deploy a lightweight instance, such as a T2.micro EC2 instance, to monitor the Auto Scaling group and update the Route 53 record accordingly when a new instance is launched. This approach makes sense given the project's small scale and the fact that only a single instance is present.

  • Configure a network load balancer in front of the Auto Scaling group, then create a Route 53 Alias record to route requests to the load balancer. — This option introduces unnecessary costs by using a load balancer, which is excessive for just one instance.
  • Create an Alias record in Route 53 targeting the Auto Scaling group's ARN, without needing any dynamic updates. — Route 53 does not support pointing directly to an Auto Scaling group ARN; Alias records require supported targets like load balancers or CloudFront distributions.
  • Set up a CloudWatch Event Rule that listens for launching or terminating events from the Auto Scaling group. Configure this rule to trigger a Lambda function, which modifies the CNAME in Route 53 to match the new EC2 instance's private DNS. — While this solution is serverless and modern, it is unnecessarily complex, and the combination of Lambda plus event bridging can be more expensive for low-frequency, single-instance scenarios.

Tip: For very small, non-critical environments with minimal scaling, it can be both simple and cost-effective to automate DNS updates with a script running on a micro instance, rather than using more advanced or costly AWS services. If you wanted to minimize costs further, a Lambda function with a CloudWatch Schedule could be viable, but the EC2 micro instance approach is straightforward for beginners.
