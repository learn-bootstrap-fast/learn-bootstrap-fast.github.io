The most reliable and direct way to ensure your SQL update script runs exactly once with each deployment in Elastic Beanstalk is by using a 'Solo Command' in your configuration files. The Elastic Beanstalk service coordinates the execution environment so the Solo Command is executed a single time on only one instance, effectively avoiding race conditions or duplicate migrations.

Choosing 'Leverage an EC2 metadata check to see if the instance is the leader...' is not an accurate or natively supported method in Elastic Beanstalk deployments; there is no built-in Auto Scaling group leader concept for reliable scripting in this context.

Modifying the database security groups as stated in 'Adjust the RDS security group to permit write access solely from one EC2 instance...' is an insecure and administratively challenging workaround, introducing possible points of failure and single-instance dependence. It is not advisable for production or automated deployments.

'Include a Container command with the leader only setting enabled...' is close—in Elastic Beanstalk, container commands with 'leader_only: true' can be used, but Solo Command is specifically designed for this use-case and is the best-practice approach preferred by AWS for idempotent, singleton operations during a deployment.

  • Tip: Use Solo Commands for tasks requiring only one execution regardless of the fleet size during Elastic Beanstalk deployments.
  • Do not rely on EC2-level metadata lookups for coordination in this scenario.
  • Security group changes as a singleton enforcement tool are not scalable or reliable.
