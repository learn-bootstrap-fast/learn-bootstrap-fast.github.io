Leverage a CloudFormation stack to provision and export output values for shared resources. Allow other stacks to retrieve those resources using the Fn::ImportValue function. is the most appropriate approach, as it enables a clear separation of shared resources (like security groups) from application-specific stacks. By exporting outputs in the 'shared' stack, other stacks can reference them via the Fn::ImportValue function, ensuring reusability while maintaining independence and preventing unnecessary updates or recreations.

The option Deploy shared resources within a CloudFormation stack, then have dependent stacks access these via the Fn::GetAttr intrinsic function. is incorrect because Fn::GetAtt is typically used to obtain attributes from resources within the same stack, not across stacks.

Embed the shared resources as part of a common stack, then nest this stack within each app’s CloudFormation stack by utilizing the AWS::CloudFormation::Stack resource. is not ideal, as using nested stacks results in tight coupling, making management of shared resources independent of application stacks more difficult. Updates to the common nested stack can affect all child stacks, reducing flexibility.

Create a stack for shared resources and then, within the AWS console, choose 'Import resources into stack' to allow other CloudFormation stacks to reuse these managed AWS resources. is a misconception. The 'Import resources into stack' feature is designed for resource adoption, not for reusing resources across multiple stacks.

  • Tip: Use Outputs and exports in dedicated CloudFormation stacks for reusable infrastructure elements, and reference them in other stacks with Fn::ImportValue.
