The correct approach is to declare the resources for export in the Outputs section of the network stack and import them into the application stack using the Fn::ImportValue function. This enables cross-stack reference between resources managed by different CloudFormation stacks. By doing so, you ensure the application stack can dynamically reference outputs from the network stack, while still allowing each stack to be managed and updated independently.

Let's examine why the other options are incorrect:

  • Specify the network resources as exported properties within the resource definitions of the network stack, and in the application stack, retrieve them using the Fn::GetAtt function.
    This is not possible because Fn::GetAtt cannot retrieve resources across stacks in this manner. Resources must be shared through outputs and imported via explicit functions designed for cross-stack referencing.
  • Output the required values in the Outputs section of the network stack, then import them into the application stack using Fn::Sub.
    Fn::Sub substitutes variables within a string and does not import outputs across stacks; it doesn't provide cross-stack import capabilities.
  • Export necessary items from the network stack using Fn::ExportValue, and use Fn::FindInMap to import these resources in the application stack.
    While Fn::ExportValue is used behind the scenes during cross-stack imports, Fn::FindInMap is only meant to retrieve values from mappings declared within the same stack and cannot be used for cross-stack outputs.

Tip: Using outputs and Fn::ImportValue is the standard way to reference values from one CloudFormation stack in another, ensuring loose coupling and modular management of your infrastructure.
