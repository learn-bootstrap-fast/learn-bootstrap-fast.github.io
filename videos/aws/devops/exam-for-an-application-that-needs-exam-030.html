The best answer is Leverage an IAM role with fine-grained permissions allowing access only to relevant items in the DynamoDB table. This approach enables you to set up an IAM role with policies that enforce user-level access control—such as access to only items with a certain partition key value. When integrated with identity federation, you can map users from a third-party IdP to temporary credentials assumed via this IAM role, securing each user's access to their own data only, while avoiding the complexity and security risk of individual IAM users per application user.

Register the app with a third-party identity provider and use web identity federation to delegate temporary AWS credentials to users comes close; however, without configuring an IAM role with precise permissions targeting DynamoDB items based on user identity, access would not be sufficiently restricted per user.

Have every user sign up as an IAM User to directly access the application is not scalable or secure for user bases numbering in the thousands. AWS IAM Users are intended for administrators or organizational staff, not external app users.

Let users authenticate with a third-party IdP and create an IAM User for each in AWS for access control is unnecessarily complex and goes against best practice, as the intent of identity federation is to avoid having to create individual IAM Users for each app user.

Tip: AWS recommends using IAM roles with web identity federation for scalable, secure, and granular access. Use fine-grained IAM policies to restrict DynamoDB access based on user context (e.g., 'PrincipalTag' in IAM policies).
