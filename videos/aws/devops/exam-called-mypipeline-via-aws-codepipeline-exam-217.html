The correct event pattern is { \"source\": [ \"aws.codepipeline\" ], \"detail-type\": [ \"CodePipeline Stage Execution State Change\" ], \"detail\": { \"state\": [ \"FAILED\" ], \"pipeline\": [ \"myPipeline\" ] } }. This pattern specifically matches failures that happen at the stage level for your named pipeline, thus ensuring notifications are only sent when a distinct stage in myPipeline fails. 

  • { \"source\": [ \"aws.codepipeline\" ], \"detail-type\": [ \"CodePipeline Pipeline Execution State Change\" ], \"detail\": { \"state\": [ \"FAILED\" ] } } is incorrect because it targets failures at the entire pipeline execution level, not the granular stage level. This could cause missed notifications for individual stage failures.
  • { \"source\": [ \"aws.codepipeline\" ], \"detail-type\": [ \"AWS API Call via CloudTrail\" ], \"detail\": { \"eventSource\": [ \"codepipeline.amazonaws.com\" ], \"pipeline\": [ \"myPipeline\" ] } } is not suitable, as this pattern triggers on all API operations via CloudTrail for the pipeline, generating noise and irrelevant alerts.
  • { \"source\": [ \"aws.codepipeline\" ], \"detail-type\": [ \"CodePipeline Action Execution State Change\" ], \"detail\": { \"state\": [ \"FAILED\" ], \"pipeline\": [ \"myPipeline\" ] } } is more granular, matching individual actions rather than stages. This may result in excessive alerting for internal action-level failures, many of which may be retried or not as significant as a stage-level failure.

Tip: When monitoring a pipeline for failed stages via CloudWatch Events/EventBridge, always match the detail-type to CodePipeline Stage Execution State Change and filter on state as FAILED to ensure precise and actionable notifications. Granularity is crucial to avoid alert fatigue or missing critical failures.
