The best choice is DynamoDB table where read throughput significantly surpasses write throughput by 100x, with CloudFront used for caching. Here’s why:

  • Your workload is predominantly read-heavy (100:1 ratio). Thus, provisioning a table to specifically handle much higher read operations optimizes both performance and cost.
  • CloudFront is well-suited for caching highly popular items worldwide, especially the top 1% of frequently accessed scores, reducing DynamoDB’s read load further and distributing content with low latency.

The other options don't align as well for these reasons:

  • DynamoDB provisioned to handle 100 times more reads than writes, using ElastiCache for caching results. While ElastiCache is great for low-latency in-memory caching, it is typically best fit for complex query or stateful application caches rather than large-scale read optimization for global, uniformly accessed APIs. CloudFront offers global edge caching that can better target the top 1% of popular data.
  • DynamoDB with balanced read and write capacity, leveraging CloudFront for caching hot data. Using equal read and write capacity provisioning under-provisions the read side and may result in throttling, given the 100:1 access ratio.
  • DynamoDB table with comparable read and write capacity, integrated with DAX caching. DAX is a DynamoDB-specific in-memory cache and does help with read-heavy workloads, but paired with equal read/write throughput, it isn’t tailored to your needs and would not fully take advantage of the API’s read-heavy traffic patterns.

Tip: Always align provisioned capacity with real-world request patterns. For read-heavy systems, ensure read capacity is prioritized, and use caching with a worldwide distribution where hot data is intensely accessed. CloudFront excels at caching frequently requested content, especially for API endpoints fetching high-score data.
