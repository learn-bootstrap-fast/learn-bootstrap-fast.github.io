The best approach is to declare the parameter in the user parameters of the CodePipeline stage and then retrieve it from the event object passed to the Lambda function. When CodePipeline invokes a Lambda function as an action in a stage, it passes a JSON event. Any user parameters set on the action are included in the event['CodePipeline.job']['data']['actionConfiguration']['configuration']['UserParameters'] field within this JSON. This allows you to efficiently and securely pass values, such as a URL, from your pipeline definition directly to the Lambda execution environment for each invocation.

The option \"Use an API Gateway endpoint that CodePipeline triggers, passing the parameter as a querystring to the Lambda function behind the API Gateway\" adds unnecessary complexity, introducing another service (API Gateway) just for parameter passing, and is less secure and efficient than direct event transmission.

\"Initiate a CloudFormation stack within the Lambda function, using the CodePipeline parameter with the “!Ref” intrinsic function for value resolution\" is incorrect because CloudFormation is meant for infrastructure as code, not for transient parameter passing in runtime workloads like Lambda function invocations within pipelines.

\"Specify the value as an environment variable in the new CodePipeline stage and access it in Lambda, for example in Python using os.environ[\"Parameter_Name\"].\" is also incorrect. Lambda environment variables are set at deployment time, not dynamically per pipeline execution, so you can't use this method to pass different values each run directly from a CodePipeline stage.

Tip: Always prefer using CodePipeline's user-defined parameters for passing context-specific values to Lambda actions, as this method is secure, auditable, and integrates natively with AWS services.
