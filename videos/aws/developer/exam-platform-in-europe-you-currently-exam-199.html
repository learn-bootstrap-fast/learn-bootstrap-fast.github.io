The correct answer is Create one Cloud Spanner multi region instance using nam eur asia1 and size capacity to keep average CPU near 45 percent so clients can read from the nearest replicas.

This design follows Google guidance for high availability with a single globally distributed Spanner instance that spans multiple continents. The multi region configuration provides synchronous replication with quorum writes across regions and can serve low latency reads from nearby replicas while maintaining strong consistency where applicable. Managing one global instance keeps operations simple because there is a single schema and no application level sharding, and sizing for about 45 percent average CPU preserves headroom for spikes and failover events.

Run three separate Cloud Spanner regional instances in europe-west1 us-central1 and asia-east1 and split tenants by continent with application logic is wrong because it fragments data and shifts complexity into the application. It does not provide transparent cross region failover or global consistency, and it complicates operations and rebalancing as tenants grow or move.
