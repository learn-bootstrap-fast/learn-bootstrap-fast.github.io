The correct choice is Provision Cloud Spanner using a multi region instance configuration because it delivers strongly consistent transactions, supports relational tables alongside a native JSON data type, and scales across continents to keep user latency low.

Cloud Spanner provides external consistency for reads and writes, horizontal scalability, and a relational schema with SQL. It also includes a JSON column type so you can combine structured columns with semi structured attributes in the same database. A multi region instance configuration synchronously replicates data across regions and automatically handles failover, which preserves strong consistency while serving a global user base with low latency.

Create a Bigtable instance with clusters in three regions is not a fit because Bigtable is a wide column NoSQL store without a relational schema or multi row ACID transactions, and multi cluster routing can yield eventually consistent reads. It does not offer SQL or native transactional semantics needed for strongly consistent multi table operations.

Deploy AlloyDB for PostgreSQL with cross region read replicas does not meet the requirement because the primary is single region and cross region replicas are asynchronous. This means no strongly consistent multi region writes or transactions, even though AlloyDB supports relational data and JSONB within one region.

Use Firestore in Native mode is not appropriate because Firestore is a document database rather than a relational system and it does not provide a relational schema or SQL. While it offers multi region locations and transactions for documents, it is not designed for globally distributed strongly consistent relational workloads.
