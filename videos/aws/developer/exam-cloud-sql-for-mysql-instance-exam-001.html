The correct option is Use Cloud SQL serverless export to write the backup to a Cloud Storage bucket.

This method offloads the export from the database instance to a managed Cloud SQL service that reads data without consuming the instance compute resources and writes directly to Cloud Storage. It is designed for large datasets like an 8 TB MySQL database and it keeps the application available while minimizing performance impact. It also reduces operational effort because it is a fully managed workflow that integrates with IAM and Cloud Storage so you can secure the artifacts with encryption and access controls.

Create a read replica and run mysqldump from the replica is not ideal for an 8 TB database because a logical dump is slow and resource intensive which can cause significant replica lag and still requires you to manage dumping and transferring data to Cloud Storage. This adds operational overhead and does not minimize performance impact as effectively as the managed export feature.

Clone the instance and run mysqldump on the clone increases cost and operational effort because cloning an 8 TB instance takes time and storage and you still need to run a long and heavy logical dump. This approach provides little benefit compared to a managed export that avoids the need for an extra instance.

Set up Datastream to capture changes from the database into Cloud Storage provides change data capture for integration and analytics but it does not produce a consistent full snapshot that you can restore as a backup. It is meant for replication of changes rather than backup and restore.
