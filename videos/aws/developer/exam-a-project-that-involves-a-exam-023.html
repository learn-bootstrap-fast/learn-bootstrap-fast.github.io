The correct options are Introduce a caching layer with Cloud Memorystore to store hot keys and reduce read load and Refine Firestore queries and maintain targeted composite indexes to improve selectivity.

Adding a cache in front of the database offloads the hottest reads and returns responses from memory which is much faster than fetching from the primary store. This reduces per request latency for interactive features and it also cuts Firestore read operations which lowers cost. With careful TTLs and invalidation for frequently accessed keys you can keep the behavior consistent while improving p95 latency and protecting the backend during traffic spikes.

Tuning queries and keeping the right indexes increases selectivity so that lookups hit precise index entries and avoid unnecessary document reads. Better selectivity and index only lookups reduce tail latency and lower the total reads billed. Focus on matching filters and ordering to available indexes and remove unneeded fields from projections so that the database does less work for each interactive request.

Migrate the workload to Cloud Spanner to gain automatic horizontal scaling is not the best fit because it increases complexity and cost for a migration that is not required to meet the latency target.
