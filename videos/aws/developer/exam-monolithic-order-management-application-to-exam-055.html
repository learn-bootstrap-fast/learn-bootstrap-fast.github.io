The correct answer is Create a dedicated data access service that mediates all database interactions and incrementally reroute calls to new service specific Cloud SQL databases.

The data access service creates a single boundary through which the monolith and new microservices interact with the database. You can gradually redirect specific operations to new service scoped Cloud SQL databases while keeping the rest on the original instance. This supports incremental decomposition with feature by feature cutovers, reduces risk through easy rollback, and lets you enforce service ownership of data without breaking existing functionality.

This approach aligns with the strangler pattern because it allows you to introduce new data stores alongside the legacy database and to progressively move reads and writes. It also enables compatibility layers such as request level routing, dual writes with verification, and phased migration of tables or aggregates which helps minimize production impact.

Refactor the single database into separate schemas that map to each service and allocate distinct connection pools for those schemas is not sufficient because it preserves a single database instance and a shared failure domain. Teams remain tightly coupled on schema changes and resource contention and you do not achieve true service level data ownership or independent scaling.

Migrate the monolithic Cloud SQL database to Cloud Spanner and have every microservice share the same Spanner database to reduce contention is a heavy migration that does not solve the core coupling since all services still share one database. Moving to Spanner adds complexity and cost and it is unnecessary for an incremental path that seeks minimal impact.

Perform an immediate split of customer, order, and product tables into separate Cloud SQL instances and update the application to use them is a big bang change with high risk. Cross database joins and transactions become difficult to manage and the blast radius is large, which conflicts with the requirement for an incremental migration with minimal production impact.
