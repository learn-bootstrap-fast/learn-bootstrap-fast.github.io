The correct choice is Turn on automated backups and binary logging and restore with point in time recovery.

Point in time recovery in Cloud SQL works by first restoring from the most recent automated backup and then replaying the change logs to the exact timestamp you choose. That is why you must have automated backups enabled and you must retain the binary logs for the duration required. With these configured, you can restore to any moment within the configured retention window to meet the compliance requirement.

Enable high availability failover for the Cloud SQL instance addresses uptime and failover during infrastructure or zonal issues. It does not protect against accidental deletes because the deletion is synchronously replicated to the standby and there is no way to roll back to an earlier point without PITR.

Configure automated backups with a 10 day retention period allows you to restore only to the timestamp of a specific backup. This does not allow recovery to an arbitrary point between backups, so it does not meet the requirement for exact point in time restoration.

Create a read replica and promote it if data is deleted does not solve the problem because replicas receive the same changes and deletions, often within seconds. Promoting a replica would typically preserve the same data loss and it still would not provide an exact point in time restore.
