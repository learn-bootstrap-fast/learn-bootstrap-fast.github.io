The correct options are Add Cloud SQL read replicas to distribute read traffic and Use connection pooling to reuse database sessions efficiently.

Adding read replicas moves a significant portion of read traffic away from the primary instance which reduces CPU and I O pressure during storage resize operations. This helps keep latency steady when the primary is busy extending storage because the replicas continue to serve read queries while the primary focuses on writes and the resize task. With a highly available primary you still keep failover capabilities while scaling read capacity horizontally with read replicas.

Implementing connection pooling reduces the overhead of creating and tearing down many PostgreSQL connections which can be expensive and can amplify latency during heavy load and resize events. By reusing existing sessions and limiting the number of active backends, connection pooling stabilizes resource usage and helps the database maintain predictable performance as storage grows.

Set a preferred maintenance window during low traffic hours does not address the problem because automatic storage increases are not tied to the maintenance window and will still occur when thresholds are crossed during peak hours.

Add exponential backoff and retry logic in the client can mask symptoms but it does not remove pressure from the database during storage resizing and will not keep performance steady under sustained load.

Turn off automatic storage increase risks running out of disk space during peak periods which can cause outages and is not recommended for a mission critical system. It also avoids the real need to scale storage safely under load.
