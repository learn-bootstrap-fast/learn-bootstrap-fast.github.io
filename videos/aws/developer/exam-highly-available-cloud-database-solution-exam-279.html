The correct option is Deploy a multi regional Cloud Bigtable instance with clusters in several continents and run streaming pipelines with Cloud Dataflow.

This design provides massive horizontal scalability and very low latency for write heavy telemetry and time series style data. By adding clusters in multiple regions it keeps reads and writes close to users while maintaining high availability and consistent performance under heavy load. The streaming pipelines can perform stateful and windowed computations for leaderboards and dispatch optimization in near real time and they integrate well with a globally replicated key value store.

The workload demands predictable performance at global scale with tens of thousands of updates per second and rapid consumption for analytics. A replicated wide column store with multi cluster routing avoids cross region coordination on every write and scales with key distribution which is a strong fit for this pattern.

Adopt Firestore in native mode with a multi regional location and rely on real time listeners to process updates is not suitable for sustained ultra high write throughput and global low latency writes. Real time listeners target application synchronization rather than large scale streaming analytics and the service has hot spotting and per document write constraints that make heavy aggregations and leaderboards difficult at this scale.

Use a regional Cloud SQL for PostgreSQL instance with read replicas and publish changes on Pub/Sub to replicate across regions centralizes all writes on a single primary which becomes a bottleneck and increases latency for distant clients.
