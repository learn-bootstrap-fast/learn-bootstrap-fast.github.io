The correct option is Run EXPLAIN ANALYZE on the problematic SQL to inspect the actual execution plan.

This method executes the query and returns the real plan with timing and row counts for each node, which lets you pinpoint exactly where time is being spent. You can see whether a sequential scan, a nested loop, a costly sort, or a hash operation is responsible, and you can validate whether estimated rows match actual rows to uncover poor statistics or missing indexes. Running it in your client against Cloud SQL for PostgreSQL gives direct, query-path evidence so you can make targeted fixes.

Add a read replica to the Cloud SQL instance is for scaling read workloads and improving throughput. It does not tell you which step inside the query plan is slow, and it can even hide the underlying inefficiency by distributing load rather than fixing the cause.

Monitor CPU and memory charts in the Cloud Console provides high level instance health and confirms symptoms like high utilization, but it does not reveal where within the query plan the time is spent. It cannot isolate the root cause in the execution path.

Implement a caching layer such as Memorystore in front of the query may improve response time by avoiding execution for cache hits, but it does not diagnose why the query is slow. It leaves the root cause unresolved and fails when the cache is cold or invalidated.
