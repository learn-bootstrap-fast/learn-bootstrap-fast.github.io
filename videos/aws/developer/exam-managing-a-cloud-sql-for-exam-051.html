The correct option is Enable automated backups and configure the backup window to align with the daily 45 minute low traffic period.

Cloud SQL automated backups provide consistent backups without taking the instance offline so availability is maintained. By setting the backup window during the observed lull you minimize performance impact while ensuring that backups complete reliably. Enabling this feature also supports disaster recovery through restore capabilities such as point in time restoration when configured, which meets the requirement to preserve data and quickly recover from failure.

Implement database sharding based on access patterns is unnecessary for this problem and adds complexity to schema design and operations. It does not address the requirement to perform routine maintenance safely during the low traffic period and it does not inherently improve disaster recovery for a single production instance.

Migrate the application database to Cloud Spanner is a major replatforming effort that is not justified by the stated need. The goal is to maintain availability and consistency for an existing Cloud SQL for MySQL workload, and a migration would introduce risk and delay rather than providing a simple maintenance solution.

Disable binary logging to improve write throughput undermines disaster recovery because you lose the ability to perform point in time recovery and it also impacts replication features. Any small gain in write performance would directly conflict with the recovery objectives of the scenario.
