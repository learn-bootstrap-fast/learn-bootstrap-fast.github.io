The correct option is Inspect the slow query log and Performance Schema and optimize the most CPU intensive queries.

This choice follows the principle of measure then optimize. Elevated CPU on a Cloud SQL for MySQL instance is most often driven by inefficient queries or missing indexes, so the least disruptive and most effective first step is to identify the worst offenders and tune them. This approach targets the actual source of contention and can yield immediate and lasting improvements without changing infrastructure or restarting the instance.

Starting with query analysis also minimizes user impact. You can gather evidence, add indexes, and refactor queries incrementally, and you can validate improvements with Cloud Monitoring. If CPU pressure remains after tuning, you can then consider scaling or topology changes with a clear understanding of the workload.

Create a Cloud SQL read replica and route reporting queries to it is not the best first step because it does not reduce CPU consumed by writes on the primary and it can introduce replication lag and additional operational complexity. Creating a replica can also add load during initial synchronization and does not fix inefficient queries.

Increase the instance machine type to add more vCPUs can mask the problem and often requires a restart which is more disruptive. It may provide only temporary relief if the underlying queries are inefficient, and some workloads will not scale linearly with additional vCPUs.

Shard the application database across multiple Cloud SQL instances is a major architectural change and is highly disruptive. Sharding should only be considered after profiling and optimizing the workload and after exhausting simpler options such as indexing, query tuning, and right sizing.
