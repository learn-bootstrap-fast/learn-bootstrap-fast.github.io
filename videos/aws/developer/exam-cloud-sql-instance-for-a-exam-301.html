The correct option is Set up Cloud Scheduler to trigger a Cloud Function that uses the Cloud SQL Admin API to start the instance before work begins and stop it after business hours.

This approach aligns with the predictable nine to five schedule and turns the instance on only when needed. It reduces compute charges during nights and weekends while keeping the database available to testers during working hours. It also uses managed services that eliminate server maintenance and keeps operations simple and reliable.

Enable high availability on the Cloud SQL instance and move the maintenance window to Saturday nights does not reduce cost for an idle instance. High availability increases cost and a maintenance window only controls when maintenance occurs rather than when the instance runs.

Purchase a three year committed use contract for Cloud SQL vCPU and memory to reduce the hourly rate regardless of usage may lower the unit price yet it still charges for running resources even when the database is idle. It also introduces a long commitment that is not ideal for a preproduction environment that benefits more from starting and stopping.

Run a small Compute Engine VM that uses a cron job to call gcloud commands to stop the instance after hours and start it each morning can work but it adds cost and operational overhead to run and secure a persistent VM. A managed schedule and serverless function avoids this extra management.
