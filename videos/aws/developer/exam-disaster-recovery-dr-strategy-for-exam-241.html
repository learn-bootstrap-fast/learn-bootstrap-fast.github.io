The correct options are Configure Cloud Spanner as a multi-region instance with synchronous replication and automatic failover and Enable cross-region replicas for Cloud SQL and plan promotion on failure.

The first choice uses Cloud Spanner multi region replication where writes commit after a quorum across regions and failover is automatic. This design delivers an effectively zero recovery point and a very short recovery time during a regional outage which satisfies an RPO under one minute and an RTO under five minutes for a mission critical transactional workload.

The second choice relies on Cloud SQL cross-region replicas that receive changes from the primary and can be promoted during a regional failure. With careful monitoring, low replication lag, and automation for promotion and traffic cutover, Cloud SQL cross-region replicas can meet the RPO under one minute and the RTO under five minutes for many transactional deployments.

Schedule regional Persistent Disk snapshots and plan instance restores is too slow and too coarse for these goals. Snapshots are periodic so the recovery point is tied to the snapshot interval and restores commonly exceed five minutes which fails both objectives.

Store regular database backups in a multi-region Cloud Storage bucket and restore when needed is a backup strategy rather than a high availability design. The recovery point depends on the last backup which is usually far longer than one minute and the restore time typically exceeds five minutes.

Use a single region Cloud Bigtable deployment and rely on manual exports does not survive a regional outage and it is not a relational transactional database for this scenario. Manual exports and imports also produce long recovery points and recovery times.
