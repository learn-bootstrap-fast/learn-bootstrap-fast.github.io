The correct options are Partition frequently read tables in the schema based on time or key access patterns and Create read replicas and route reporting traffic to them.

Using read replicas offloads the dashboard queries from the primary so the production writer remains unchanged. Cloud SQL for MySQL supports replicas that handle read only workloads which increases aggregate read throughput and reduces latency when you route reporting traffic to them.

Applying partitioning to the most heavily read tables helps queries scan less data and keep indexes smaller which improves cache efficiency and lowers latency during peak reads. This schema optimization complements replicas and does not change the writer role.

Enable Cloud SQL high availability for the primary instance improves resilience and failover but it does not add read capacity because the standby does not serve traffic in normal operation.

Increase the machine type of the primary instance adds CPU and memory yet all reads still hit a single node which leaves you with the same contention between reads and writes during peak dashboards.

Move the primary to a larger persistent disk tier with higher IOPS can lower storage latency but it does not provide horizontal read scaling and all read traffic still competes on the primary.
