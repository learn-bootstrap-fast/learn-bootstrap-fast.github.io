The correct option is Create a dedicated service account for the microservice and assign the Cloud SQL Client role.

This choice follows the principle of least privilege and good workload isolation. Giving the microservice its own service account limits blast radius and improves auditing and revocation. The client role provides the minimal IAM permissions needed to connect to Cloud SQL through the connectors or the Auth Proxy without granting administrative abilities. You would still manage database user access at the PostgreSQL level or use IAM database authentication as appropriate.

Create a new service account and grant it the Cloud SQL Viewer role is incorrect because the viewer role only allows viewing instance metadata and logs. It does not permit establishing a connection to the database through the proxy or connectors.

Reuse the existing service account that is used by the batch data loader for this instance is incorrect because sharing service accounts across workloads violates least privilege and separation of duties. It increases blast radius, complicates auditing, and makes lifecycle management harder.

Create a new service account and grant it the Cloud SQL Editor role is incorrect because the editor role includes permissions to modify Cloud SQL instances and configurations. That is unnecessary for a reporting microservice that only needs to connect and read, and it grants excessive privileges.
