The correct option is Introduce a database proxy or data access facade that routes requests to service-specific data stores while incrementally carving functionality out of the monolith.

This approach creates a single controlled entry point for data access so you can gradually route reads and writes to new service-owned stores while the legacy database continues to serve unaffected functionality. It enables clear ownership because each service assumes control of its own schema behind the facade and it supports independent scaling because the routing layer can direct traffic to separately scaled backends. Cutover downtime can be kept under two minutes because you switch routing in a quick and reversible step once validation is complete which avoids intrusive database migrations during the final switchover.

Set up Datastream or another change data capture pipeline to replicate changes from the monolith into separate service databases and have services read from their own copies while writes continue to the legacy system is not sufficient because it leaves the write path centralized in the monolith which prevents true ownership and independent scaling. It also introduces eventual consistency lag and read anomalies that can cause user-visible disruption and it makes the final write cutover complex.

Migrate the existing schema unchanged to Cloud SQL and allow every microservice to connect directly to that shared instance preserves a shared database bottleneck and tight coupling among services. It fails the goals of clear service data ownership and independent scaling and it increases blast radius and coordination overhead.

Maintain the monolith database and replicate each domain into separate Cloud Spanner instances for use by individual services adds cost and operational complexity while still depending on the monolith for primary writes. Without a routing facade you cannot safely transition traffic service by service and you risk consistency and dual-write challenges that do not meet the low-downtime requirement.
