The correct option is Refactor the application into independently deployable services first and then migrate each service's schema and data in stages to its own Cloud Spanner database.

This approach supports daily releases because each service can be deployed and tested independently once it owns its schema and data. You can migrate incrementally by carving out one service at a time and backfilling or dual writing as needed, which keeps customer impact minimal since the rest of the monolith keeps running. Cloud Spanner provides horizontal scalability, strong consistency, high availability, and online schema changes, so it can handle traffic that spikes by eight times while preserving transactional integrity.

Decoupling the data per service removes cross team and cross release contention. Each service can scale independently and you avoid a risky big bang cutover. This pattern aligns with incremental modernization strategies that safely migrate functions from a monolith while maintaining stable user experiences.

Place Apigee in front of the monolith and continue routing all reads and writes to the single database until every new service is deployed does not address the core bottleneck because the shared database remains a single point for all writes and scaling. It delays the necessary data decomposition and leads to a large risky cutover later rather than enabling incremental migrations and independent releases.

Split the monolithic schema into multiple schemas within a single Cloud SQL instance that align to services and allow services to perform cross schema joins when needed keeps a single primary for writes which limits scale during peak events. Cross schema joins preserve tight coupling across services and hinder independent deployments, and vertical scaling or read replicas cannot overcome primary write limits for sustained eight times spikes.

Redesign the relational schema into documents and collections and move every service to Firestore requires a wholesale data model change that is unlikely to be low impact. Firestore is a document database without relational joins and is not an easy drop in replacement for a transactional relational monolith, so this path adds significant risk and effort without clear benefit for the stated goals.
