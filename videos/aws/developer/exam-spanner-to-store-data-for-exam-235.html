The correct option is Increase node count based on measured read and write throughput and adjust nodes as traffic and storage grow.

Cloud Spanner performance scales horizontally with compute capacity. The right way to keep p95 latency consistent is to measure actual read and write throughput and observe latency and CPU utilization, then increase or decrease capacity to match. As traffic and stored data grow, adding capacity keeps request queues short and reduces contention, which sustains low tail latency. Teams can adjust capacity manually or use autoscaling to react to changing load patterns.

Reduce the number of nodes to optimize for cost and rely on client retries to mask occasional latency spikes is not appropriate because reducing capacity increases queuing and contention which raises tail latency. Client retries add more work and time that users experience and they do not meet a strict p95 latency objective.

Create a multi-region instance so data is replicated to multiple regions for better performance globally does not address the core scaling need for the stated workload. Multi-region configurations improve availability and geographic reach, yet they introduce higher write latency due to cross region consensus and they do not inherently provide the consistent low p95 latency required for writes.

Break the schema into more tables to make queries and updates faster is not a reliable way to achieve consistent low latency. Performance issues are more often caused by insufficient compute capacity, hot spots, or suboptimal indexing rather than the number of tables, so arbitrary table proliferation does not solve the scaling requirement.
