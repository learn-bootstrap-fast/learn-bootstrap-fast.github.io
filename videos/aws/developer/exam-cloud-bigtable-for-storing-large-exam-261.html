The correct option is Use SSD storage for the Bigtable cluster that powers dashboard queries. The other choices either reduce performance, increase cost without benefit, or are not supported.

Interactive dashboards that must return in milliseconds rely on low latency random reads, and this storage type is recommended by Google Cloud for production user facing workloads. It provides the throughput and tail latency characteristics needed for the hot 21 day working set. Retaining older data for compliance does not change the requirement for fast access to recent data, and you can keep costs in control by right sizing nodes and using garbage collection policies rather than selecting a slower medium.

Configure HDD storage for the primary cluster that handles live user reads is not appropriate because that medium is optimized for large sequential scans and has significantly higher read latency. It would harm the interactive experience for dashboard users.

Deploy Bigtable with cross region replication to multiple regions for faster reads does not address the latency requirement for a single region dashboard and it adds substantial cost and operational overhead. Replication is primarily for availability and disaster recovery and it can also add write latency.

Enable automatic tiering between SSD and HDD within one Bigtable instance is not possible in Bigtable. The storage type is chosen at cluster creation and you cannot mix or automatically tier storage types within the same instance.
