The correct option is Use Cloud Bigtable for the low latency workload and perform real time analytics on the same data.

Cloud Bigtable is designed for very high throughput and low latency workloads and it can scale to tens of millions of reads and writes per second while sustaining single digit millisecond response times. It can easily retain tens of terabytes of event and time series data in a wide column schema that matches clickstream and gameplay patterns. You can run streaming and batch analytics directly on the same dataset by connecting Dataflow or Spark to Cloud Bigtable or by using change streams to power real time derived views without moving the primary store.

Stream events into BigQuery and use Dataproc with the BigQuery Storage API to process large datasets is not appropriate for a low latency event store. BigQuery is an analytical warehouse and its streaming ingestion and serving model include latency and quota constraints that do not meet tens of millions of operations per second with millisecond access.

Deploy Cloud Spanner with a regional configuration and use Dataflow to export to Cloud Storage for Dataproc analysis does not fit the requirement. Cloud Spanner excels at globally consistent relational workloads and SQL but it is not the best choice for ultra high throughput key value style event ingestion at this scale. Exporting to files for analysis adds processing delay and prevents real time analytics on the same store.

Store events in Firestore and use Dataflow with Firestore connectors to analyze the data cannot meet the target throughput and latency. Firestore is a document database optimized for application development and it has write patterns and quota limits that are not intended for tens of millions of operations per second or for very large hot partitions.
