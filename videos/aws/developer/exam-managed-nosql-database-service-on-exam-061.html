The correct approach is Use Firestore in Datastore mode with automatic sharding and elastic scaling.

This service is fully managed and automatically partitions data and scales request throughput which allows it to absorb abrupt surges from hundreds to tens of thousands of requests per second while keeping performance steady. It requires no capacity planning and no manual node changes which aligns directly with the requirement for hands off elasticity and a durable NoSQL backend for customer activity data.

Create a Cloud SQL for PostgreSQL instance and add several read replicas to handle spikes in reads is not a NoSQL solution and replicas only help reads while writes still funnel to the primary. It also depends on manual sizing and replica management and it does not provide the automatic elastic scaling needed for sudden traffic spikes.

Deploy Bigtable with a static three node cluster in each zone and increase nodes by hand during busy periods does not meet the requirement because it explicitly relies on manual scaling and a fixed starting size. The service can scale very high but this configuration would throttle during surges until an operator intervenes which violates the need for automatic capacity adjustments.

Provision Memorystore for Redis with a fixed 64 GB tier to buffer traffic spikes is a cache rather than a primary durable NoSQL database. It has fixed capacity and eviction risk under pressure and it is not intended to be the system of record for this workload.
