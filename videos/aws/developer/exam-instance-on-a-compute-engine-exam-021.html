The correct option is Enable the MySQL Performance Schema and analyze wait events and lock contention using the events_waits_summary_global_by_event_name and events_statements_summary_by_digest tables.

This method provides in process instrumentation of waits and statements so you can see whether time is being spent on disk I O waits, on row or table locks, or on CPU execution inside MySQL. The events_waits_summary_global_by_event_name table aggregates waits by event type which lets you identify contention on file I O and various lock types. The events_statements_summary_by_digest table summarizes statements by digest with total and average latency and related counters so you can distinguish time spent executing from time spent waiting and quickly pinpoint the main offenders.

The option Install the Ops Agent on the VM and review CPU, memory and disk metrics in Cloud Monitoring dashboards is not sufficient because it only exposes operating system level utilization and cannot reveal MySQL wait events or lock contention. It can help you see a busy host but it does not verify database level contention.

The option Enable the general_log in MySQL to capture every SQL statement and then parse the log for slow operations is unsuitable for diagnosis of this issue because it records every statement and adds significant overhead while providing no insight into wait categories such as locks and I O. It is noisy and lacks the structured wait and latency breakdown you need.

The option Migrate the database to Cloud SQL and use Query Insights to review query activity and latency is unnecessary and disruptive for an urgent investigation on a Compute Engine VM. It would require a migration and does not address the immediate need to verify contention on the current host.
