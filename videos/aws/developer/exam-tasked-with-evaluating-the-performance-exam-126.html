The correct choice is Create a single region Cloud Spanner instance.

A Cloud Spanner regional deployment provides horizontally scalable write throughput and very low read latency while preserving strong consistency and full ACID transactions across multiple rows and tables. Keeping the instance in one region reduces cross region latency and keeps costs controlled compared with multi region configurations while still offering high availability within the region.

Utilize a sharded Cloud Firestore instance in Native mode is not suitable because Cloud Firestore is a document database that does not excel at complex relational workloads and its transactions are designed for small sets of documents and have per transaction limits that constrain complex multi row operations at very high throughput. Sharding does not change the transactional model or remove these limits.

Provision Cloud SQL for PostgreSQL with high availability and multiple read replicas is not a fit because only the primary in Cloud SQL handles writes and replicas are read only. This means write throughput cannot scale horizontally and would become a bottleneck as demand grows even though PostgreSQL supports ACID transactions.

Use a multi region Cloud Bigtable instance with 4 clusters in different regions is incorrect because Cloud Bigtable does not support multi row ACID transactions. Multi region replication adds cost and can increase write latency and replication between clusters is not strongly consistent which conflicts with the transactional requirement.
