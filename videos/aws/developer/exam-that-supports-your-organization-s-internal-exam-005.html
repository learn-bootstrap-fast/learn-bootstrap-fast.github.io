The correct option is Enable Cloud SQL Insights and review the longest running and most frequent queries. This provides immediate visibility into what is actually consuming resources and it does so without risky changes to the production instance.

It lets you see query level statistics such as execution time, frequency, waits, and locking so you can pinpoint which statements are driving the CPU peaks and rising connection counts. With this information you can validate whether the slowdown is caused by a few inefficient queries, missing indexes, or excessive concurrency, and you can then apply targeted fixes with confidence.

Create one or more read replicas for the database is not the right first step because replicas only offload reads and they require application changes to route read traffic. They do not reduce write load on the primary and they do not address the underlying cause of the slow queries. Replication lag can also introduce new issues during busy periods.

Resize the primary instance to a larger machine type may temporarily mask the symptoms and it adds operational risk because changing machine type triggers a restart. If the root cause is inefficient queries or excessive connections then more CPU will not solve the problem efficiently.

Place a global external load balancer in front of the database to spread connections is not appropriate for Cloud SQL. Fronting a managed database with a global HTTP or TCP load balancer is not supported as a way to multiplex database sessions and it does not solve query level bottlenecks. Connection pooling at the application layer is the recommended approach instead.
