The correct option is Create a log based metric in Cloud Logging for MySQL \"lock wait timeout\" entries and attach a Cloud Monitoring alert policy.

Lock contention in MySQL produces a clear signal in the logs through the lock wait timeout message. Cloud SQL forwards these logs to Cloud Logging, and creating a log based metric that counts those entries allows you to trigger an alert policy when the count rises. This targets the exact symptom and provides near real time detection because log ingestion and alert evaluations occur frequently. It reduces noise and speeds investigation since alerts fire only when actual lock waits are observed.

Create a Cloud Monitoring alert on the Cloud SQL CPU utilization metric when it rises above 80% is not a good indicator of lock contention. Locks can occur even when CPU is moderate, and high CPU can be caused by many unrelated issues, which makes this a noisy and unreliable signal for this problem.

Run a scheduled job that queries performance_schema lock wait views every 20 minutes and publish the findings to Pub or Sub introduces long detection delays and additional operational overhead. A twenty minute polling interval is too slow for a busy promotion window, and Cloud SQL already exports logs that can be used for faster and simpler alerting.

Create a Cloud Monitoring alert for the Cloud SQL Active connections metric when it exceeds 95 percent of the configured limit does not directly measure lock waits. Connection count can be high for many reasons and lock contention can be severe even when connections are well below the limit, so this metric does not reliably detect the issue.
