The correct answer is Create a clone of the existing instance and select SSD storage for the clone, then redirect traffic to the clone after validation. This provides a rapid move to faster storage while the current instance continues to serve users, which keeps disruption minimal and reduces disk wait time.

SSD persistent disk in Cloud SQL delivers much higher write IOPS and lower latency than HDD, which directly addresses increased p95 write latency and I O wait. The operation creates a point in time copy on a new instance where you can choose SSD while the source remains online. After validating the new instance you can switch application connections, which keeps the cutover window very short and avoids extended downtime.

Export the database and restore it into a new Cloud SQL for PostgreSQL instance that uses SSD storage, then point the application to the new instance is slower and more disruptive because exporting and importing large datasets takes significant time and often requires a read only window to ensure consistency. This increases the risk of extended downtime during a busy period.

Add a high availability configuration with an SSD backed standby and initiate a failover to the standby does not solve the performance issue because Cloud SQL HA uses the same storage type as the primary and you cannot assign a different storage type only to the standby. HA can also add write latency and is intended for resilience rather than upgrading storage performance.

Provision a read replica on SSD storage and perform a failover to make it the primary is not appropriate because Cloud SQL does not support failover to a read replica.
