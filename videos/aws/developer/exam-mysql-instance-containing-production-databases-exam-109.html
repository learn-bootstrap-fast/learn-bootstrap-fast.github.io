The correct choice is Enable Cloud SQL automated backups and schedule the backup window during off peak traffic.

Automated backups are the Cloud SQL recommended approach for reliable recovery because they use managed, incremental storage level snapshots and integrate with restore workflows. They are dependable and can be paired with binary logging to enable point in time recovery. By setting the backup window to off peak hours you reduce the impact on a high throughput workload and keep production latency and throughput stable.

Create a Cloud SQL read replica and run scheduled exports from the replica to Cloud Storage is not ideal because exports are logical dumps that do not offer the same recovery guarantees as managed backups. A replica can lag behind the primary so the export may not represent a precise point in time and the export process still consumes resources and adds I O load.

Run mysqldump from the primary instance and write the dump files to Cloud Storage increases CPU and I O load on the primary and may require long running transactions or locks to achieve consistency. This directly affects a busy checkout workload and does not minimize production impact.

Run a Cloud SQL serverless export of all databases to Cloud Storage on a regular schedule still performs a logical export that lacks point in time recovery and often has longer and more manual restore steps. Even if some processing is offloaded the data must still be read from the instance which can impact throughput.
