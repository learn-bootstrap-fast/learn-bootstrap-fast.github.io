The correct architecture is Implement event-driven services using Cloud Functions for purchase and inventory workflows and store seat inventory in Firestore to deliver real-time updates to clients.

This serverless event-driven design scales quickly during short bursts and remains highly available without manual capacity planning. Cloud Functions scales automatically as requests and events arrive so it can absorb a three minute surge to tens of thousands of users. Firestore provides low latency reads and writes with transactional updates to prevent overselling and it offers native real-time listeners so clients receive seat availability changes immediately.

Deploy Google Kubernetes Engine for microservices and persist data in Cloud SQL while using Memorystore to cache hot seat data is not the best fit because Cloud SQL can become a connection and write throughput bottleneck during extreme spikes and caching introduces staleness risks for inventory.
