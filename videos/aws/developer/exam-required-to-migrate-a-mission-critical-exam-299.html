The correct choice is Configure Datastream to capture changes from the on premises PostgreSQL source and continuously apply them to Cloud Spanner before redirecting traffic.

This approach lets you perform an initial load and then keep Cloud Spanner in sync through continuous change data capture. You can validate replication lag and data consistency, pause writes briefly on the source, allow the final changes to apply, and then redirect traffic. The brief cutover window can meet the 60 second requirement while preserving transactional integrity because the pipeline replays ordered changes and checkpoints progress.

Export the full PostgreSQL database to files and then import the dump into Cloud Spanner as a single batch is a bulk offline process that requires extended downtime and cannot guarantee a 60 second cutover. It also risks divergence if the source continues to accept writes during the import.

Use Database Migration Service to move the on premises PostgreSQL database directly into Cloud Spanner is not supported because Database Migration Service does not target Cloud Spanner. It is designed for migrations into Cloud SQL and AlloyDB rather than into Spanner.

Modify the applications to write to both the existing PostgreSQL database and Cloud Spanner at the same time introduces dual writes which are prone to inconsistency and lost ordering under failures. It complicates application logic and does not ensure data integrity during cutover.
