The correct option is Run DR drills in an isolated blue green environment that is kept in near real time sync with production using replication, then execute failover and validation there.

This approach mirrors production with minimal risk because replication keeps the standby environment close to current state while isolating tests from live traffic. You can validate failover runbooks by promoting a replica and exercising routing, application connections, and data integrity checks without introducing downtime or additional load on the primary instance. Cloud SQL supports read replicas and cross region replicas, so you can practice a controlled promotion and verify recovery objectives while preserving production availability.

Use Database Migration Service to create a temporary copy of production in a separate project each week and run DR drills against the copy is not appropriate because the service is optimized for migrations rather than recurring disaster recovery exercises. It adds replication overhead to production and does not provide realistic failover mechanics, so it will not validate procedures like replica promotion and cutover that you must prove in a true recovery scenario.

Manually stop the production primary database and start the disaster recovery procedure to verify the plan creates an avoidable outage and introduces significant risk to a real time payments API. Compliance testing should not jeopardize availability, and there is no need to disrupt the primary when an isolated synchronized environment can be used.

Perform the recovery exercise during a planned maintenance window on the production system still impacts the live system and can extend beyond the window if issues arise. Maintenance windows are intended for patching and routine updates, not for full recovery drills that are better executed in an isolated replica environment.
