The correct option is Identify and tune the most expensive queries using Query Insights or pg_stat_statements.

High and sustained CPU utilization on a Cloud SQL for PostgreSQL primary is most often driven by inefficient or high volume queries. Google recommends starting with observability and query tuning because it provides the biggest improvement at the lowest cost with minimal disruption. You can use Query Insights to find the statements that consume the most CPU time and to view latencies, execution counts, and patterns over time. You can also enable pg_stat_statements to capture cumulative statistics for each normalized query and then optimize the worst offenders by rewriting queries, adding a targeted index, or adjusting query parameters. This approach addresses the root cause rather than masking it.

Distribute the database across multiple Cloud SQL instances by sharding the data is not the first step because sharding adds significant complexity, requires application changes, and introduces operational overhead. Cloud SQL does not provide managed sharding and cross shard queries and transactions become harder, so this is a last resort after you have exhausted tuning and simpler scaling options.

Increase the instance's vCPU allocation by moving to a larger machine type can temporarily reduce CPU pressure but it may only mask inefficient queries and raise costs. Vertical scaling might still be needed later, but recommended practice is to profile and fix the top queries first and then right size the instance based on measured improvements.

Change the database schema and create additional indexes across several columns should not be done blindly because unnecessary or broad indexes can slow writes, increase storage, and may not help the real hotspots. Schema or index changes should be driven by findings from Query Insights or pg_stat_statements so that you add only targeted indexes that benefit specific expensive queries.
