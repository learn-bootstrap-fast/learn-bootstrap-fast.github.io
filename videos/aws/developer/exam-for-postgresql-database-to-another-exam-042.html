The correct option is Create a cross region read replica in the destination region then plan a brief maintenance window and promote the replica to primary.

This approach keeps continuous replication running to the target so the data is nearly up to date before cutover. You schedule a short window to stop writes to the source, confirm the replica has no lag, and then promote it. The promotion operation is fast and the application can reconnect to the new primary in the destination region which keeps downtime well under five minutes and ensures the target is fully consistent at switchover.

Use Database Migration Service to run an offline one time migration that stops writes during export and import is not appropriate because an offline migration requires writes to be stopped for the entire export and import period. For a production database this outage commonly exceeds five minutes even though it would be consistent.

Perform a manual export with serverless export then import the dump into a new instance in the destination region results in a long service interruption if you need strict consistency. You must stop writes before export and keep them stopped until the import finishes which typically takes longer than five minutes for nontrivial datasets.

Restore from a recent automated backup into a new instance in the destination region and then point the application to the new instance does not guarantee full consistency at switchover unless you halt writes well before the backup. Restores can also take longer than five minutes and any writes after the backup time would be lost without a controlled replication or log shipping process.
