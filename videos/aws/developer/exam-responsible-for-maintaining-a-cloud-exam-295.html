The correct option is Refactor the schema and add or adjust indexes to optimize query performance. This approach targets the bottlenecks inside PostgreSQL and can deliver significant speedups with minimal ongoing cloud cost, which aligns with the requirement to keep extra spend under fifteen percent.

Index and schema optimization reduces I O and CPU by allowing the planner to avoid full scans and to use selective access paths. You can analyze slow queries with EXPLAIN ANALYZE and add composite or covering indexes that match common predicates and sort orders. You can use partial indexes if the two hour peak concentrates on a subset of rows. You can also remove unused or redundant indexes that slow writes and ensure autovacuum and ANALYZE keep statistics current. These changes usually add only modest storage overhead and little to no extra instance cost while improving throughput during peak hours.

Create a read replica to offload read only workloads during peak traffic is not the best first step because it only helps read traffic and requires application changes to route reads. A replica adds another instance that increases monthly cost and it does not improve write performance or badly tuned queries. Replica lag during a busy window can also reduce its usefulness.
