The correct options are Implement a caching layer with Cloud Memorystore for hot data and Adopt a data design that uses partitioning sharding and well tuned indexing.

The first choice offloads frequent reads from the primary databases to an in memory store, which cuts latency and reduces database CPU and IOPS. With fewer expensive reads hitting the backend you can often use smaller instance sizes or fewer replicas which lowers cost while maintaining reliability through a managed service that supports high availability.

The second choice improves how data is organized and accessed. Splitting large datasets by time or key range reduces the amount of data scanned per query and distributing data across shards removes hotspots. Well considered indexes let the engine find rows quickly which shortens execution time and reduces resource consumption. These practices improve performance and can reduce spend without compromising durability or availability.

Move every workload to Cloud Bigtable to gain high throughput characteristics is not appropriate for all database workloads. Bigtable is excellent for very large scale wide column and time series access patterns but it does not provide relational features such as joins and multi row transactions. For typical transactional workloads this migration can increase complexity and cost rather than improve both objectives.

Enable compute autoscaling for Cloud SQL instances to absorb traffic surges is incorrect because Cloud SQL does not automatically scale CPU and memory for a single instance. You must change machine shapes or add read replicas, and storage can autoscale but compute does not, so this choice would not deliver the promised benefit.

Use Cloud SQL with automated backups and binary logging disabled undermines reliability. Disabling backups and binlog removes point in time recovery and complicates replication, which risks data loss. Any small cost savings would come at the expense of the reliability requirement.
