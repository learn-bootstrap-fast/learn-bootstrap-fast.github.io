The correct answer is Use the official Firestore client libraries in the application to perform operations and rely on their managed connection handling.

The client libraries are designed for Firestore and they handle persistent connections using efficient protocols and manage retries and backoff. This lets each Cloud Run instance initialize a Firestore client once and reuse it across requests which reduces connection overhead and keeps latency low. Authentication uses application default credentials so you avoid extra networking setup. This approach aligns with stateless Cloud Run scaling because new instances spin up quickly and immediately benefit from the client libraries connection management.

Configure Private Service Connect or VPC peering and open region specific connections from Cloud Run to Firestore is unnecessary for this use case. Firestore is exposed as a Google API and Cloud Run can reach it directly without private networking. Adding Private Service Connect or peering adds complexity and does not improve latency for this scenario.

Proxy all database calls through a Cloud Functions service that caches Firestore connections using Cloud Memorystore is counterproductive. A proxy adds an extra hop and more latency and Memorystore cannot cache logical database connections. The better pattern is to call Firestore directly from Cloud Run with the client libraries.

Issue HTTP requests to the Firestore REST endpoint and create and close a new connection for each request increases overhead due to repeated TLS handshakes and lack of connection reuse. It also bypasses the efficiencies and resiliency that the client libraries provide.
