The correct option is Create a Cloud Function that calls the Cloud SQL Admin API to start and stop instances and invoke it with Cloud Scheduler on weekday mornings and evenings.

This approach uses the supported start and stop operations in the Cloud SQL Admin API so you can pause compute charges outside working hours while still paying for storage and backups. Pairing the API with a scheduled trigger allows you to align with the weekday 8.30 a.m. to 7.00 p.m. local time window. It has very little operational effort because the components are serverless and managed and Cloud Scheduler supports time zones so you can run the jobs at the correct local times without maintaining any servers.

Enable high availability on the Cloud SQL instances and configure a preferred maintenance window is not relevant because high availability addresses failover and maintenance timing and it does not control when instances run or stop. It will not reduce costs during off hours.

Purchase Cloud SQL committed use discounts for a one year term for all developer and test instances is not a fit because commitments favor steady and predictable usage. These sandboxes are idle most evenings and weekends so a commitment would not turn off resources and can lead to paying for capacity you do not use.

Provision a small Compute Engine VM and run a cron job that uses gcloud to start and stop the Cloud SQL instances on a weekday schedule could work but it increases operational overhead and risk because you must patch and monitor a VM and manage service accounts. The question asks for very little operational effort which the serverless scheduling solution achieves more effectively.
