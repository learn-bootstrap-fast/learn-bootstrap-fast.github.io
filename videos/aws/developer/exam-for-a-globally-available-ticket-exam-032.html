The correct options are Use interleaved tables so that child rows are stored with their parent rows to keep related data co-located and Define a composite primary key that starts with a high-cardinality column to distribute writes evenly.

Use interleaved tables so that child rows are stored with their parent rows to keep related data co-located aligns with Cloud Spanner guidance for modeling hierarchical relationships where queries frequently access parent and child together. Interleaving physically co-locates related rows which reduces cross-partition lookups and improves transactional locality for operations like retrieving a reservation with its line items or payments. When used appropriately with one to few or controlled one to many relationships this pattern keeps related data efficient to query.

Define a composite primary key that starts with a high-cardinality column to distribute writes evenly addresses the write hotspot issue. Spanner partitions data by key ranges and concentrates writes to the leader of the affected ranges. A high-cardinality leading key spreads incoming writes across many ranges and leaders which helps avoid hotspots and preserves write throughput during large imports and steady traffic.

Choose a composite key whose first column has few distinct values to keep the index small is wrong because a low-cardinality leading key concentrates many rows into a few ranges which increases the risk of hotspots. Index size is less important than ensuring even key distribution for write scalability.
