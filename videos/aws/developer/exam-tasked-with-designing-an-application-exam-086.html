The correct option is Establish VPC peering between the application VPC and the database VPC. It provides private RFC 1918 connectivity over the Google backbone and delivers very low regional latency without introducing proxies or load balancers.

VPC peering enables direct routing between VPC subnets while keeping traffic inside the Google network which means no public IPs and no internet exposure. It works across projects and lets the GKE workloads in app-core reach the Compute Engine database in data-store using only internal addresses. In the same region such as us-central1 the path is short and typically within a few milliseconds which satisfies the sub 3 ms requirement.

Use Cloud VPN with IPsec between the two VPC networks is not suitable because it terminates on public IP endpoints and traverses the public internet which violates the no internet exposure requirement and adds overhead that can prevent sub 3 ms latency.

Publish the database behind an internal TCP load balancer and connect using Private Service Connect does not meet the constraint because it explicitly introduces a load balancer and a service endpoint that the team wants to avoid. It also adds extra hops and complexity that are unnecessary for simple private connectivity between VPCs.

Use Cloud Interconnect to reach the database from the application VPC is intended for connecting on premises networks to Google Cloud rather than connecting two VPC networks. It would not provide a direct in region VPC to VPC path and would add cost and operational overhead without benefit.
