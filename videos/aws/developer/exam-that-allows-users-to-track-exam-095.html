The correct choice is Use Firestore in Native mode to keep traveler profiles as documents and trigger a Cloud Function on document writes that streams the delta into BigQuery.

This approach matches the need for a flexible schema because Firestore documents can add or remove fields without migrations. A Cloud Function triggers on each create, update, or delete and uses BigQuery streaming inserts so changes arrive within seconds which comfortably meets the two minute freshness requirement. It is event driven and eliminates polling while scaling well with spiky write patterns.

Use Cloud Spanner with Change Streams and run Dataflow to write each change into BigQuery is not ideal because Spanner requires a predefined relational schema and adding or removing fields requires DDL and coordinated deployments. Although change streams with Dataflow can deliver low latency, the rigid schema and higher operational overhead do not match the need for frequent ad hoc field changes in traveler profiles.

Use Firestore in Datastore mode and schedule periodic exports that load entities into BigQuery cannot meet the near real time requirement. Exports are batch operations that write to Cloud Storage and then load into BigQuery which introduces significant delay. Datastore mode also lacks native document write triggers which makes it less suitable for automatic per change propagation.

Use Cloud SQL with separate tables for profiles and preferences and run a Cloud Scheduler job that invokes a Cloud Function to copy rows into BigQuery relies on scheduled copying and is not event driven. It cannot guarantee propagation within two minutes and the relational schema would require ongoing migrations to handle fields being added or removed by users.
