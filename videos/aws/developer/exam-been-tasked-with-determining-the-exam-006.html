The correct option is Use Firestore client libraries in the Cloud Run service and assign the service account the needed IAM roles. This uses Google managed service account identity with application default credentials to obtain tokens for Firestore and keeps calls on the standard Google APIs path which supports the stated read and write volume and meets low latency needs.

This approach is the supported and most efficient way for Cloud Run to access Firestore in Native mode. The client library handles IAM authentication, secure connections, retries, and efficient use of HTTP sessions. You simply grant the Cloud Run service account the minimal roles required to read and write documents so you get strict security with least privilege and no user managed keys.

Configure Serverless VPC Access and VPC Network Peering to establish a private connection from Cloud Run to Firestore is not appropriate because Serverless VPC Access connects to resources in your VPC and Firestore is a Google API reached over the Google front end. VPC peering does not provide access to Firestore and private access to Google APIs would require Private Service Connect for Google APIs which is not needed for these requirements.

Place an external HTTP load balancer in front of Firestore and direct clients to the closest regional endpoint is not possible because you cannot place your own load balancer in front of Firestore. Firestore already exposes managed endpoints and the client libraries route to the correct regional service when you choose the Firestore location.

Run the Cloud SQL Auth Proxy with the service and connect to Firestore over the proxy using SSL is incorrect because the Cloud SQL Auth Proxy is only for Cloud SQL and it does not support Firestore. Firestore already uses TLS and IAM so adding this proxy would not work and would not improve security.
