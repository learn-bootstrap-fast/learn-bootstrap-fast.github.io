The correct option is Enable Cloud Bigtable replication with two or more clusters in different zones and direct traffic to a hot standby cluster during recovery.

Bigtable replication stores your tables in multiple clusters across zones which increases durability because there are independent copies of the data. During an outage you can meet a ten minute recovery time objective by routing traffic to the standby cluster using multi cluster routing or by updating your clients to target the healthy cluster. This approach restores service quickly because there is no bulk data movement during failover.

Schedule daily Cloud Bigtable exports to Cloud Storage and restore with the Bigtable import tool when needed is too slow for a ten minute objective. Exports introduce a recovery point of up to a day and imports of large tables take far longer than a few minutes.

Periodically copy Cloud Bigtable data into Cloud SQL and use the Cloud SQL copy as the recovery source is a poor fit because Cloud SQL is a relational service and does not match Bigtable scale or access patterns. The copy process and any cutover would exceed a ten minute objective.

Use Dataflow with Cloud Bigtable change streams to continuously write mutations to Cloud Storage and recover by replaying files adds durability outside Bigtable but replaying mutations from files at scale is complex and usually cannot restore service within ten minutes.
