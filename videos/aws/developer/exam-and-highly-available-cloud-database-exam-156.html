The correct option is Deploy a multi region Cloud Spanner instance with multiple read write replicas and route clients to the nearest replicas by location.

This design places read write replicas in multiple regions and commits through a globally coordinated consensus which gives external consistency for transactions and worldwide high availability. Routing clients to the closest read write replica keeps both reads and writes under the stated latency target for major regions while all commits remain strongly consistent across the globe.

It also scales elastically by adding nodes and automatically splitting and rebalancing data to sustain very high throughput. Automatic failover and maintenance further protect availability which aligns with the needs of a global payments platform.

Create a multi cluster Cloud Bigtable deployment across two continents with multi cluster routing for low latency access is incorrect because replication with multi cluster routing is eventually consistent and it does not provide multi row transactional semantics or globally consistent cross region writes.
