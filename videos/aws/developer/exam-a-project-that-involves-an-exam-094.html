The correct options are Add a caching layer with Cloud Memorystore and Create Cloud SQL read replicas in one or more regions.

Add a caching layer with Cloud Memorystore reduces read load on the primary database by serving hot keys from memory which keeps read latency low during promotions that drive traffic to many times normal. Offloading frequent reads to Memorystore is typically a cost effective way to boost performance and absorb spikes without resizing the database and it improves user experience by returning data quickly.

Create Cloud SQL read replicas in one or more regions helps scale out read traffic and improves resilience. Placing read replicas close to users lowers read latency and offloads the primary during peak demand. Replicas can be promoted if needed which supports recovery scenarios. When paired with Cloud SQL high availability for the primary instance this pattern aligns with the 99.95 percent availability target and controls cost better than a wholesale platform migration.

Migrate the database to Cloud Spanner is not the best first step because although Cloud Spanner delivers strong consistency and very high availability it usually increases cost and adds migration complexity. The requirements favor keeping latency low and improving reliability without a large increase in cost which is better met by caching and replicas on Cloud SQL.

Replace Cloud SQL with BigQuery is incorrect because BigQuery is an analytical data warehouse and it is not designed for low latency transactional reads and writes that power a storefront.

Move the workload to Cloud Bigtable is also incorrect because Cloud Bigtable is a wide column NoSQL store that lacks relational transactions and SQL features. Moving a transactional retail database to it would require major redesign and is unlikely to meet the stated goals with minimal cost increase.
