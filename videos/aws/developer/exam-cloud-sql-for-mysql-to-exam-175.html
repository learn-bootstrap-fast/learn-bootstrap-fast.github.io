The correct choice is Cloud SQL instance with a primary in one zone and a read replica in another zone within the same region. This keeps traffic within the primary region for low read and write latency and gives resilience to a zonal outage because the nearby replica can be promoted if the primary becomes unavailable.

This setup balances high availability needs with a practical disaster recovery path without introducing cross region latency. Reads can be offloaded to the replica to reduce load on the primary. If the primary zone fails you can promote the replica to restore write availability which meets the requirement to keep service responsive for users in the primary region.

Cloud SQL instance with a primary in one region and a read replica in a different region on the same continent is more suitable for cross region disaster recovery but the replication is asynchronous and promotion is manual which does not satisfy high availability. It also introduces additional network distance for reads from the replica and potential replication lag that is not needed when your users are concentrated in a single region.

A single zonal Cloud SQL instance has no redundancy and a zonal failure would cause an outage. It does not meet high availability or disaster recovery requirements.
