The correct answer is Configure a custom Cloud Monitoring metric that samples the pg_stat_activity view for active query counts and alert when the count spikes abnormally.

This approach captures the signal that best correlates with sudden latency because pg_stat_activity shows active and waiting sessions in near real time. By sampling frequently and writing to a custom metric in Cloud Monitoring you can use a short alignment window and tight alerting thresholds so the next spike triggers immediately and preserves context about concurrent activity. This lets you identify blocked sessions, bursts of concurrent queries, or connection storms and you can add helpful labels such as database or user to speed root cause analysis.

Route Cloud SQL logs to BigQuery with the Log Router and schedule a query every 30 minutes to flag slow statements is batch oriented and delayed. Brief spikes can appear and vanish within minutes so a thirty minute schedule can miss them and it only informs you after the fact when valuable transient evidence may be gone.

Create a Cloud Monitoring alert that triggers when CPU utilization goes above 95% to signal potential resource pressure watches a coarse proxy rather than the cause of query latency. Lock contention, connection saturation, or storage stalls can drive latency while CPU remains moderate and this alert neither detects those reliably nor identifies the specific statements involved.

Build a script that scans PostgreSQL logs stored in Cloud Storage for slow query patterns and execute it every 14 days is not proactive or timely. Waiting weeks to analyze logs will not help you capture the next spike and offline scanning cannot notify you in real time.
