The correct option is Provision a new Cloud SQL for MySQL 8.0 instance, run Database Migration Service in continuous mode to replicate from the 5.7 source, then perform a brief cutover.

Using DMS in continuous mode performs an initial load and then streams ongoing changes from the MySQL 5.7 source using binary logs so the MySQL 8.0 destination stays nearly caught up. At cutover you pause writes on the source, wait for replication to reach zero lag, and then update the application to point to the new Cloud SQL instance. This approach routinely achieves a few minutes of downtime and preserves transactional integrity because changes are replayed in order.

Create a Cloud SQL read replica of the MySQL 5.7 instance and promote the replica during a maintenance window to minimize downtime is incorrect because a read replica shares the same major version as its primary. Promotion does not change the version, so you would still be on MySQL 5.7 and you would not meet the requirement to upgrade to 8.0.
