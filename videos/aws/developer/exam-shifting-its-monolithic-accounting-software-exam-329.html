The correct choice is Place API Gateway in front of the services and have the microservices use a shared Cloud Spanner database to retain strong transactional consistency during the cutover.

Cloud Spanner provides fully relational storage with strongly consistent distributed ACID transactions across tables which is essential when the system relies on strict transactional guarantees across many requests. It scales horizontally and offers high availability with automatic replication and online schema changes so the platform can evolve while keeping downtime to a minimum. Using API Gateway in front of the services helps you centralize traffic control and authentication and it allows a controlled cutover so you can shift clients to the new microservices with a brief and predictable interruption that fits within the fifteen minute goal.

Provision a separate Cloud SQL instance for each microservice and migrate the related tables to that instance is not suitable because splitting data by service breaks the ability to execute strict ACID transactions across services. Cross instance or cross database transactions are not supported in a way that would preserve the required consistency which increases complexity and risk during cutover.

Adopt a single high availability Cloud SQL instance with one consolidated schema for all microservices and plan to split it later allows ACID in the short term but it undermines the microservices goal of independent scaling and autonomy. The later split introduces significant data migration effort and higher disruption risk and the managed failover and maintenance behavior of this choice can still introduce brief outages that work against the tight downtime target during a complex refactor.

Partition the monolithic schema into column families stored across multiple Cloud Bigtable clusters and connect each microservice to its portion does not meet the requirement because this store is not a relational database and it does not provide multi row or multi table ACID transactions. It only guarantees atomicity within a single row which cannot satisfy strict transactional consistency across many requests and services.
