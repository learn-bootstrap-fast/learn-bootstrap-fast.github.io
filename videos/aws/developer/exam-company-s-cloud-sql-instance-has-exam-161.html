The correct option is Enable the slow query log in Cloud SQL for MySQL and set long_query_time to three seconds, then create a metric from logs in Cloud Monitoring that filters slow query entries and configure an alerting policy to notify when matches occur.

This approach turns on the built in slow query log so every statement exceeding the threshold is written to Cloud Logging. By setting long_query_time to three seconds you get an authoritative record of slow statements at the database level without modifying applications. You can create a logs based metric that filters the mysql slow entries and then attach a Cloud Monitoring alerting policy so notifications are sent automatically when matches occur. This uses native services and keeps custom code to a minimum.

Instrument the application to publish a custom metric of query durations to Cloud Monitoring and set an alert when the metric is above three seconds is not ideal because it requires code changes in every caller and can miss queries from tools or services that do not use your instrumentation. The database already emits the needed signals in its logs.

Route Cloud SQL logs to Pub Sub and process them with a Dataflow job that identifies long running statements and publishes notifications adds unnecessary complexity and ongoing code to maintain. Cloud Logging and Cloud Monitoring can filter logs and alert directly so a custom pipeline is not needed.

Create a Cloud Function triggered by Cloud Scheduler to call the Cloud SQL Admin API every minute and scan for long running connections and send an alert will not reliably detect per query execution times and the Admin API does not expose precise query duration details. Polling each minute is also too coarse for a three second threshold.
