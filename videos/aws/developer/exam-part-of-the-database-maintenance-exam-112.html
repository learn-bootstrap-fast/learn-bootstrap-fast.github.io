The correct option is Enable the MySQL slow query log and set long_query_time, ship mysql-slow.log to Cloud Logging using the Ops Agent, and review entries in Logs Explorer.

This approach uses the built in MySQL slow query log to capture statements that exceed a threshold, which lets you identify the longest running SQL without touching application code. On a Compute Engine VM you can configure the Ops Agent to send mysql-slow.log to Cloud Logging, then use Logs Explorer to filter by duration fields and quickly see which queries are causing the latency spikes.

Configure your services to export spans to Cloud Trace and inspect traces for long operations is not appropriate because it typically requires instrumenting the application to emit spans around database calls. The requirement is to avoid code changes and tracing on a self managed MySQL VM will not automatically capture SQL statements without additional instrumentation.

Migrate the database to Cloud SQL for MySQL and analyze performance using Query Insights violates the constraint to avoid moving the workload and it is not a quick action. Query Insights is a managed feature in Cloud SQL and does not apply to a self managed MySQL instance on a VM.

Add timing statements around each database call in the application and redeploy to capture durations directly conflicts with the requirement to make no application changes and it introduces redeployment risk and delay.
