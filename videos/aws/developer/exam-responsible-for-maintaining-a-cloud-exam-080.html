The correct option is Redesign the row keys to match read access patterns so range scans are efficient and hotspots are minimized.

Cloud Bigtable partitions data by the lexicographic order of row keys and serves scans most efficiently when adjacent rows that are read together are stored together. Thoughtful row key design improves locality for range scans, reduces seeks, and minimizes hotspots on tablets which lowers read latency for very large tables. Techniques such as using a composite key that starts with the primary access dimension, applying limited salting to distribute high write rates while preserving scan contiguity, or bucketing timestamps for time series workloads are all forms of row key design that improve scan efficiency. This is a routine optimization in Bigtable and it does not force changes to client query behavior because reads continue to use the same access patterns while the storage layout is optimized underneath.

Use denormalization to collapse related entities into wider rows to avoid client-side joins is not the right choice because denormalization changes the data model and can increase row size and read amplification. It does not directly address scan locality or hotspotting which are governed by the row key order in Bigtable.

Implement horizontal sharding by user region and route requests to region-specific tables would require significant application routing changes and operational overhead with multiple tables. Bigtable already scales horizontally within a cluster and this approach does not improve per-table scan efficiency or reduce hotspots in a single table.

Create a single global secondary index table maintained by Cloud Dataflow for all Bigtable tables adds complexity, write amplification, and potential consistency lag. Bigtable does not provide native secondary indexes and maintaining a custom index changes how reads are performed rather than improving the efficiency of scans within the primary tables.
