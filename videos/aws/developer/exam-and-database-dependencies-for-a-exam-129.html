The correct action is Review the services codebase database schemas stored routines and SQL statements to enumerate direct and indirect dependencies.

This approach surfaces how services call each other and how they interact with the relational database. By reading the code and inspecting schemas and stored routines you can identify connection patterns, hard coded endpoints, transaction boundaries, triggers, and procedural logic that the application relies on. This produces a reliable dependency map that informs sequencing, compatibility checks, and testing plans which directly reduces migration risk for a three tier billing platform.

Use Cloud Asset Inventory to export a list of resources and treat that output as the application dependency map is not appropriate because it inventories Google Cloud resources and policies rather than application call flows or SQL touchpoints. It does not analyze on premises systems or code, so it would miss most runtime and database dependencies.

Migrate only the database using Database Migration Service and refactor the application after cutover increases risk because it defers discovery and design until after the move. Database Migration Service moves data but it does not validate application compatibility or uncover hidden dependencies, so you could face breakage at cutover.

Use Cloud Data Fusion to produce an automatic diagram of application and database dependencies is not suitable because Data Fusion is a managed data integration service for building pipelines. It does not reverse engineer application architectures or enumerate SQL and stored procedure dependencies across services.
