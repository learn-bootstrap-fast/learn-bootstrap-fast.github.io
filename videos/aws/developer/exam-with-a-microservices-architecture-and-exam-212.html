The correct option is Add one or more read replicas for the Cloud SQL primary to serve read requests.

This approach addresses the current high read load by offloading queries from the primary, which reduces contention and can lower tail latency during peak hours. Cloud SQL for PostgreSQL supports asynchronous replicas that can be added to scale out reads, which improves throughput and provides headroom as traffic grows. It follows Google recommended practices for scaling databases while keeping the primary focused on writes and critical transactional work.

This solution also aligns with the requirement to avoid major changes. Many applications can introduce a read only connection for safe queries with minimal code updates, or can route read heavy paths to the replicas. As demand increases you can add more replicas, which reduces the chance of future problems by allowing horizontal scaling rather than repeatedly pushing the limits of a single primary.

Increase the machine type of the Cloud SQL instance to add more vCPUs and memory may offer short term relief but it is vertical scaling that does not address read scalability and will eventually hit limits. It also does not directly reduce tail latency caused by read contention and it offers less protection against future load growth than scaling out.

Migrate the database to Cloud Spanner would be a major architectural change and would require significant application and schema work. It does not meet the constraint to avoid major changes and is unnecessary for the immediate need to mitigate read driven slowness.

Split the schema across several smaller Cloud SQL instances and route traffic accordingly is effectively manual sharding, which introduces substantial application complexity and routing logic. It violates the requirement to avoid major changes and can complicate transactions and consistency without solving the problem as cleanly as replicas.
