The correct option is Create a cross region read replica in the destination region then promote it to primary and point the application to the new instance.

This approach uses a Cloud SQL read replica to continuously replicate data from asia-southeast2 to europe-west1. It scales well for a 22 TB PostgreSQL database because it relies on physical replication and it keeps the target nearly in sync while the service continues to run. At cutover you promote the replica to become a standalone primary in europe-west1 and then update the application connections which keeps downtime to a brief window.

Build a Dataflow pipeline with JDBC to stream changes from the source Cloud SQL instance into the target Cloud SQL instance is not a recommended method for Cloud SQL migrations and it lacks a managed and transactionally consistent change data capture path for PostgreSQL in Cloud SQL. Implementing this reliably would be complex and would not guarantee minimal downtime.

Use pg_dump to create a logical backup on a temporary VM and restore into the new instance with pg_restore would require very long export and import times for 22 TB and would lead to extended downtime or significant performance impact. Logical dumps are slower than replication and do not meet a minimal downtime goal for this scale.

Export tables to CSV with the PostgreSQL COPY command into Cloud Storage and import them into the target instance using COPY is a manual process that does not maintain transactional consistency across tables and provides no ongoing replication. For a multi terabyte database this would be slow and would require a long outage to achieve a consistent cutover.
