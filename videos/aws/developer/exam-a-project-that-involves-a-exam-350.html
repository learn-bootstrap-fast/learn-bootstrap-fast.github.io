The correct option is Enable clustering on the BigQuery tables using customer_id and country columns.

This choice aligns the storage layout with how analysts filter the data. The tables are already partitioned by event_date and adding clustering on customer_id and country lets BigQuery prune data more aggressively which reduces bytes scanned and lowers query cost. Queries that filter or group by these columns will scan fewer blocks and complete faster while staying on the same platform.

Clustering works especially well with large daily ingestion because it continuously organizes data within each partition based on the specified keys. This improves performance for selective predicates and common joins on those keys and it directly targets the cost driver which is the amount of data read.

Move the workload to Cloud Spanner to benefit from global relational scaling is not appropriate because that product is designed for transactional workloads and not for large scale analytical scans. Moving off the warehouse would not address scan costs for analytical queries and would add migration complexity.

Use BigQuery Reservations to buy dedicated slots for the project can improve performance predictability and throughput but it does not reduce the amount of data scanned by each query. Without very high and steady utilization it may not reduce overall cost and it does not exploit the query patterns that benefit from data pruning.

Migrate the datasets to Cloud SQL to control spend with smaller instances is not suitable for tens of terabytes per day or for columnar analytics. That service is optimized for transactional workloads and would not scale or perform well for warehouse style queries.
