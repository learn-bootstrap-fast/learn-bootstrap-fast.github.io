The correct choice is Run Database Migration Service for SQL Server with continuous data replication then validate the destination and perform a planned cutover while keeping the source writable until you confirm success.

This approach streams ongoing changes from the source to Cloud SQL so the target stays nearly current. The final cutover is a brief event where you stop writes and point applications to Cloud SQL which supports the under 25 minute requirement for a 3.2 TB database when the heavy data movement has already completed. Because the source remains intact and writable until you validate the target you have a straightforward rollback by directing traffic back to the original database if an issue appears immediately after switching.

Use Datastream to capture change data from SQL Server into Cloud SQL for SQL Server and configure reverse replication to the source for rollback is not viable because the service does not support SQL Server as a source into Cloud SQL for SQL Server and there is no reverse replication capability to sync changes back to the on premises system.

Build a Cloud Data Fusion pipeline that performs nightly full loads and run a final copy during the maintenance window and add a second pipeline to copy changes back if you need to revert does not provide continuous replication and would require a large final copy which risks exceeding the short window. It also introduces complex custom rollback logic rather than keeping the source as the simple fallback.

Export a native SQL Server backup to Cloud Storage then restore into Cloud SQL for SQL Server with SQL Server Management Studio and create a Cloud SQL read replica that points to the on-premises instance for fallback is unsuitable because native backup and restore for a multi terabyte database is a lengthy offline operation and Cloud SQL for SQL Server does not support read replicas or replication from an on premises primary.
