The correct answer is Create a read replica in asia-southeast1 and modify the application to route regional read requests to that replica.

Users in Singapore are currently reading from replicas in the United States and Europe which adds significant network round trip time. Adding a replica in asia-southeast1 places the data close to those users and the application can direct their read queries to the local replica. This approach reduces network latency during peak periods while keeping writes on the primary and maintaining read scalability.

Migrate the workload to Cloud Spanner with a multi-region configuration is unnecessary for this problem. Spanner is a different managed database with a distinct architecture and migration effort and while it offers multi region reads it is not required when Cloud SQL can solve the issue with a nearby read replica.

Increase the vCPU and memory of the primary Cloud SQL instance does not address the network distance between Singapore and the existing replicas or primary. The dominant factor here is geographic latency rather than compute capacity.

Place a global external HTTP(S) Load Balancer in front of the database to route SQL traffic by geography is not viable because the HTTP(S) load balancer handles only HTTP and HTTPS traffic and Cloud SQL instances are not exposed as load balancer backends. Database connections use private or public IP with Cloud SQL connectors rather than L7 load balancing.
