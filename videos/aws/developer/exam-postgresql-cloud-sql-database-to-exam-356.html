The correct option is Enable high availability on the Cloud SQL instance so a synchronous standby is created in another zone with automatic failover.

This configuration creates a primary and a synchronous standby in different zones within the same region. Writes are synchronously replicated to the standby which provides zero data loss at failover and very low recovery time. Because replication stays inside one region, the added write latency is minimal while still protecting against a single zone outage. The service automatically promotes the standby on failure and the instance connection endpoint moves to the new primary which keeps application changes to a minimum and speeds recovery.

Use Cloud Spanner instead of Cloud SQL to achieve global availability is not appropriate because the requirement is to keep using Cloud SQL and only tolerate a zonal outage within one region. Moving to a different product would require a migration and introduces different semantics and higher cost that are unnecessary for this scope.

Set up two independent Cloud SQL for PostgreSQL instances in different zones and place them behind a network load balancer would not work because independent instances do not replicate data and a network load balancer cannot make two separate databases act as one. Cloud SQL provides a single managed endpoint and supported replica and failover mechanisms rather than fronting instances with a load balancer.

Run PostgreSQL on Compute Engine VMs in a regional managed instance group with custom scripts to detect failure and promote a secondary is complex, error prone, and not a good fit because managed instance groups are designed primarily for stateless scaling. Building reliable synchronous replication and automatic failover yourself would be harder to operate and would not match the simplicity and reliability of the managed high availability feature.
