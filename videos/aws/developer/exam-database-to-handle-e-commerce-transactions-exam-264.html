The correct choice is Integrate Cloud SQL with a managed search platform such as Elasticsearch or OpenSearch and run searches there.

This approach offloads indexing and query load to a system designed for full text search. Search engines provide inverted indexes, relevance scoring, stemming, synonyms, and horizontal scalability that handle 250,000 SKUs with low latency. Cloud SQL remains focused on transactional workloads so you avoid contention on CPU, memory, and IOPS. You can synchronize data through change data capture or batch pipelines so the search index stays current without burdening the database.

Export transactional data to BigQuery on a schedule and run keyword searches in BigQuery is not suitable for user facing search because BigQuery is optimized for analytical workloads and not for low latency interactive keyword queries. Scheduled exports introduce staleness which undermines inventory accuracy during checkout.

Enable full text search in Cloud SQL and issue all keyword queries on the transactional instance violates the requirement to avoid performance impact. Even with GIN or GIST indexes and PostgreSQL full text features, heavy search traffic competes with OLTP workload and index maintenance increases write overhead.

Create a Cloud SQL read replica and route keyword searches to the replica reduces pressure on the primary but it still requires maintaining full text indexes and can cause replication lag under heavy search load. It also lacks the advanced search relevance and scalability of a dedicated search engine and there is still operational coupling to the database tier.
