The correct approach is Turn on automated backups and point-in-time recovery because it lets you restore to a specific moment just before an incident and keeps application downtime to a brief cutover window that can be under fifteen minutes.

Point-in-time recovery uses automated backups together with transaction logs to recreate the database state at a chosen timestamp within the retention window. You can initiate the restore to a new instance while production continues to run. When the target is ready you switch connections to the restored instance which limits unavailability to the cutover period. This directly supports a strict recovery time requirement while also providing protection against accidental deletes or data corruption.

Enable Cloud SQL high availability on the primary instances improves resilience for zonal outages and maintenance events but it does not let you roll the database back to an earlier state. If data is corrupted or deleted then that state is replicated to the standby so it does not meet the restoration objective.

Export each instance to Cloud Storage and import when recovery is needed is a manual process that is slower and scales poorly for larger datasets. It does not provide granular recovery to a moment in time and the export and import steps commonly exceed a fifteen minute recovery window.

Configure a cross-region replica for every database instance helps with disaster recovery for regional failures and read scaling but it does not restore data to a previous point since corruption and deletes are replicated. It addresses availability rather than precise recovery needs.
