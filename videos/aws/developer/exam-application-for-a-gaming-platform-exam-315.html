The correct option is Use Firestore to persist chat messages with real time listeners and trigger Cloud Functions on writes to update active user counters.

Firestore delivers low latency writes and reads and it natively pushes changes to clients through real time listeners which fits a live chat requirement. It scales automatically with serverless infrastructure and charges primarily by operations which helps control cost. The 90 day retention requirement can be enforced with document expiration using Firestore TTL policies. The live dashboard can subscribe to aggregated counters that are updated by Cloud Functions on each write which keeps the leaderboard fresh well within a 15 second target.

Store conversations in Cloud Spanner and run analytics services on Cloud Run to compute active user metrics is not the best fit because Cloud Spanner is designed for globally consistent relational workloads and is often costlier for this use case. It does not provide built in real time push to clients and would require additional components to stream updates to browsers. Managing retention would also need custom cleanup logic rather than a simple TTL policy.

Use Cloud SQL to store chat records and serve the chat application on App Engine for real time delivery is weaker for large scale chat because Cloud SQL has connection and throughput limits that can constrain spiky interactive traffic. It does not offer native real time listeners for clients which means extra caching or messaging layers would be needed to achieve instant updates and that adds complexity and cost.

Ingest messages with Pub/Sub and write them to BigQuery while using Dataflow streaming jobs to power the real time leaderboard is better suited for analytics pipelines than for serving interactive chat. BigQuery streaming inserts can have short but variable latency and are not intended to back low latency transactional reads for chat sessions. Pub or Sub is not a client facing transport for browsers and Dataflow adds continuous processing cost and complexity that is unnecessary for simple counters and dashboards.
