The correct option is Introduce a connection pooler such as PgBouncer between the application and Cloud SQL.

Cloud SQL for PostgreSQL incurs overhead for each connection and enforces connection limits, so thousands of short lived connections during a flash sale can overwhelm the instance and lead to errors. A connection pooler keeps a small set of persistent database connections and efficiently multiplexes many client sessions onto them. This smooths traffic spikes, reduces connection churn, and improves stability. In many deployments this can be introduced with only configuration changes to the connection endpoint which meets the requirement to avoid changing application logic.

Enable high availability on the Cloud SQL instance is focused on instance failover and maintenance resilience. It does not pool or limit client connections and it does not address connection storms or short lived connection overhead.

Deploy the Cloud SQL Auth Proxy on each application server and route all database connections through it provides secure authentication and connectivity but it is not a connection pooler. It does not reduce the number of backend connections and therefore does not mitigate connection spikes.

Turn on automated backups on the Cloud SQL instance protects data and supports recovery objectives. It does not influence connection management or reduce connection errors during bursts of traffic.
