The correct option is Provision a Cloud SQL read replica and direct the analytical workload to it. This keeps the heavy nightly reporting reads off the primary instance so live transactions continue without contention.

This approach maintains a near real time copy of the database through asynchronous replication. The reporting job can run complex joins and aggregations on the read only copy while the primary continues to serve writes. You can size and tune the replica independently which lets you optimize for analytics without changing the transactional workload or SQL.

The option Use Cloud Bigtable to store a replicated copy of the relational data and run the analytical queries there is not appropriate because Bigtable is a NoSQL wide column store that is optimized for large scale key based access and time series patterns. It does not natively support relational joins and complex SQL aggregations and it would require custom pipelines and query rewrites which adds unnecessary complexity.

The option Migrate the workload to Firestore to handle analytics at scale is unsuitable because Firestore is a document database designed for hierarchical access with simple indexed queries. It does not provide server side joins or multi table analytics that this reporting requires and a migration would disrupt the existing relational application without addressing the analytical need.

The option Create a Cloud SQL failover replica and point the reporting job at that instance is incorrect because a failover replica is a standby for high availability. It is not intended for read workloads during normal operation and is reserved to take over only if the primary fails.
