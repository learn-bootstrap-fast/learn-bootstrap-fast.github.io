The correct option is Enable MySQL Performance Schema and inspect the sys schema views to review wait events and statement statistics.

This approach gives visibility inside the database engine so you can see where time is actually spent. The instrumentation exposes wait events and statement digest statistics that let you determine whether the slowness comes from locking, scans, temporary tables, input and output, sorts, or other waits. On Cloud SQL for MySQL you can enable the feature with the appropriate flag and then use the helper views that summarize slow statements and high wait contributors which allows you to find the specific query pattern and the exact bottleneck rather than guessing.

Watch CPU and memory charts in Cloud Monitoring for the instance is insufficient for root cause analysis of a single slow SQL statement because instance level metrics only show resource pressure. They do not reveal which waits or statements inside MySQL are responsible.

Add a new composite index on the columns used by the query without further analysis is a guess and may add write overhead and storage without solving the actual problem. You should first confirm the access path and waits using engine instrumentation and only then design indexes with evidence.

Use Cloud Trace to profile the database request end to end is focused on distributed request latency in applications and services. It does not provide insight into internal MySQL waits or statement level statistics that are required to diagnose a slow SQL plan.
