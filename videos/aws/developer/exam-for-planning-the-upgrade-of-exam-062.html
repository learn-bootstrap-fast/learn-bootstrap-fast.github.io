The correct approach is Resize the existing Cloud Memorystore for Redis instance to a higher capacity tier in place during a planned maintenance window.

This approach vertically scales the managed Redis instance which increases available CPU and network resources and raises connection limits. That directly boosts throughput to meet the new objective while Memorystore orchestrates the change on the same endpoint. Performing the change during a maintenance window lets you control timing and minimize the brief disruption while preserving data consistency because the service manages failover and state.

Create a new Cloud Memorystore for Redis instance in a larger tier migrate the data to it and then point the application to the new endpoint introduces a cutover to a new endpoint and requires data migration that is not natively replicated between instances. This increases downtime risk and complicates consistency during the switch.

Enable read replicas on the current Cloud Memorystore for Redis instance to distribute read traffic while keeping the same tier is not viable because Memorystore for Redis does not offer user accessible read replicas. The high availability replica in Standard Tier is not readable and therefore this would not deliver the required throughput increase.
