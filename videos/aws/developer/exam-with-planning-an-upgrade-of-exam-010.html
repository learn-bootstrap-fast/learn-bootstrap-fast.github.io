The correct choice is Provision a new Cloud SQL for PostgreSQL instance on the required major version then configure external server logical replication from the current instance wait for it to catch up promote the new instance and redirect clients.

This method creates a parallel target on the newer major version and streams changes from the source using PostgreSQL logical replication. You can keep the application writing to the old instance while the target catches up. At cutover you quiesce writes, confirm replication has reached zero lag, promote the target by removing the subscription, and point clients to it. The only downtime is the brief cutover which can be kept well under two minutes while data consistency is preserved because you replicate all committed changes before redirecting traffic.

This approach is supported by Cloud SQL for PostgreSQL and uses native publications and subscriptions. You enable logical WAL on the source, publish the required tables, create a subscription on the target, and monitor replication lag. Because the target already runs the new major version, you avoid the risks and unpredictability of an in place upgrade and you have an easy rollback path by keeping the original instance intact until the switch is complete.

Perform an in place major version upgrade of the existing Cloud SQL for PostgreSQL instance from the Google Cloud console is not suitable because the instance is taken offline during the upgrade and the duration depends on data size and vacuum state. This outage can easily exceed two minutes and you have limited control and rollback options during the process.

Use Google Cloud Datastream to set up continuous replication from the current instance to a new Cloud SQL instance and then cut over to the target is not appropriate because Datastream is designed for change data capture into destinations such as BigQuery and Cloud Storage and does not provide a direct and supported path to Cloud SQL for PostgreSQL for this use case. It would require additional pipelines and orchestration which adds complexity and risk and does not align with the recommended method for Cloud SQL major version upgrades.

Export the database with pg_dump then import it into a fresh Cloud SQL instance using pg_restore and point the application to the new instance results in prolonged downtime for nontrivial databases because both export and import are offline relative to writes. This process cannot reliably meet a two minute outage window and it does not provide continuous replication to keep the target in sync prior to cutover.
