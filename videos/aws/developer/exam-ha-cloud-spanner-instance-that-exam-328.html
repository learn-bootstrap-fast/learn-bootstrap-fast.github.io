The correct choice is Provision a single Cloud Spanner instance using a Europe multi-region configuration and add read-only replicas in the regions where clients are located. This meets the requirement for responsive reads and writes across Europe while maintaining strong consistency and high availability.

A Europe multi-region instance places read write replicas in multiple European regions and uses synchronous replication with automatic failover, which keeps write latency lower for European users and preserves strong consistency. Adding read-only replicas in the regions where clients are located provides local read access and improves read throughput while all writes are coordinated by the leader region within the same multi-region configuration. This design gives a single logical Spanner instance that can host many databases and scales horizontally for both capacity and availability.

Create two Cloud Spanner instances in one European region with high availability enabled and attach read-only replicas in every region where the applications run is not suitable because it concentrates writes in a single region which increases write latency for remote users and leaves you exposed to regional failure. Read only replicas do not change the write path and they cannot convert a single region deployment into a true multi-region write configuration.

Build two Cloud Spanner instances in different European regions with HA turned on and add read-only replicas in each region that hosts clients is incorrect because separate instances do not share data transparently. You would need application level replication to keep them consistent and you would lose the single system of record that Spanner multi-region provides.

Deploy four separate Cloud Spanner instances in different regions with HA and place read-only replicas in each application region is also incorrect because it fragments data across many instances and cannot deliver strongly consistent reads and writes from a single database.
