The correct option is Create a Cloud SQL read replica of the on premises MySQL using the external primary feature, promote the Cloud SQL replica during cutover, and configure an external read replica that pulls from Cloud SQL back to the on premises server for rollback.

This approach uses the external primary capability so Cloud SQL continuously replicates from the self hosted MySQL. You can plan the cutover by promoting the Cloud SQL replica once replication lag is near zero so application downtime is kept within the fifteen minute window. For a practical fallback, you can configure the original on premises MySQL as an external replica of Cloud SQL after promotion so if problems arise you can redirect traffic back to the source while it stays nearly in sync. This provides both low downtime migration and a clear rollback path using standard MySQL replication.

Use Database Migration Service for continuous replication to Cloud SQL, then plan rollback by restoring a recent Cloud SQL backup back to the source server is incorrect because Cloud SQL backups cannot be restored to a non Cloud SQL instance and DMS does not provide a direct reverse replication path back to the source.

Import a logical dump into Cloud SQL, then schedule daily exports from Cloud SQL back to the on premises server as a fallback is incorrect because a dump and restore typically requires extended downtime and daily exports do not provide a timely or low risk rollback and would lead to significant data loss during a failback.

Create a Cloud SQL instance with the external server feature to replicate from the on premises database, and also enable reverse replication from Cloud SQL to the on premises database for failback is incorrect because a single instance cannot act as both a replica and a primary at the same time and Cloud SQL does not support bidirectional replication on the same pair, which would risk replication loops and conflicts.
