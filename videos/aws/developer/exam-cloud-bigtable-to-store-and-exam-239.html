The correct option is Bigtable multi-cluster instance with clusters in separate regions within the same continent.

This design uses Bigtable replication to place clusters close to users while keeping another cluster in a different region for resilience. Traffic can be routed to the nearest cluster to keep read and write latency low for local users. If a region fails, clients can continue to read and write to the surviving cluster because the data is replicated across regions within the same continent, which also avoids the extra latency and costs of crossing oceans.

Bigtable multi-cluster instance with clusters in different zones inside one region cannot withstand a regional outage because all clusters are still inside the same region. This meets zonal resilience but not regional resilience.

Bigtable multi-cluster instance with clusters spread over regions on different continents would survive very large failures, yet it unnecessarily increases replication and client latency for users who are meant to be served locally. It also introduces higher intercontinental network costs and variability.

Bigtable single-cluster instance running in one zone keeps latency low only within that zone and provides no protection against zonal or regional failures, so it does not meet the high availability requirement.
