The correct choice is Run the Cloud SQL Auth Proxy as a sidecar container in each GKE pod.

This approach provides strong security with IAM based authentication and automatic TLS, and it is easy to manage because you deploy it alongside your application containers. Applications connect to a local TCP port so they do not need database credentials in the code, which simplifies secret management. When you pair this with a Cloud SQL private IP in the same region, traffic stays on the private Google network which helps minimize latency.

Establish VPC peering between the GKE VPC and the Cloud SQL network is not valid because Cloud SQL private IP uses private services access with a service producer network. You do not create a direct VPC peering to a Cloud SQL network.

Use the Cloud SQL public IP with SSL client certificates and authorized networks can be secure, yet it requires managing client certificates and source IP allow lists. GKE pods do not have stable public source IPs, so you would need extra networking to present a fixed IP. This adds operational overhead and can add latency compared to private in region traffic.

Configure Cloud NAT so the pods egress to Cloud SQL through a NAT gateway is not a connectivity method to Cloud SQL by itself. It only provides outbound internet and does not authenticate or grant access to the database. You would still need a public IP with authorized networks and a fixed source IP, which increases complexity.
