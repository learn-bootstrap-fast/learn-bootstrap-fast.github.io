The correct option is Create a full clone of the production Cloud SQL instance, upgrade the clone, run realistic performance tests, then redirect traffic to the upgraded clone.

This clone approach lets you validate engine and schema changes with production like load without risking the primary. You can benchmark queries and observe resource utilization on the upgraded clone and you can tune configuration before users are shifted. Cutover can be planned by switching connection endpoints or using a controlled DNS or connection proxy change which keeps downtime within the three minute service level objective. If problems appear after cutover then you can roll back quickly by directing traffic back to the original primary which gives a reliable and fast recovery path.

Set up a Cloud SQL cross region read replica, upgrade the replica to the new version, then promote it to primary is not viable because a read replica must match the primary database version to replicate. You cannot upgrade the replica to a new major version while it is still replicating from an older primary and promotion after an upgrade would not be supported. Even if you promoted first you would incur longer downtime and lose the easy rollback and testing benefits.

Schedule an in place upgrade on the primary and rely on automatic failover during maintenance does not provide controlled validation or a dependable rollback. Automatic failover is for unexpected outages and an in place major version upgrade can exceed the allowed downtime and leaves no quick path to revert if performance regresses.

Use the Cloud SQL maintenance window to upgrade and plan to use point in time recovery to roll back if issues occur fails the rollback requirement because point in time recovery creates a new instance and restore time commonly exceeds a few minutes. It also risks data loss between the chosen recovery point and the failure which does not meet the strict recovery expectations.
