The correct option is Perform a point in time recovery to a timestamp just before the corruption began.

This approach leverages the automated backups and the write ahead log archive to recreate the database state just before the defect started corrupting data. Because the problem was detected about 30 minutes after deployment, recovering to a timestamp just before the first corrupting transaction minimizes data loss and meets the goal of the lowest possible recovery point objective. In Cloud SQL for PostgreSQL this recovery is performed by restoring from the latest backup and replaying WAL entries up to the specified timestamp.

Force a manual failover to the Cloud SQL for PostgreSQL standby and keep the primary offline while you investigate is not appropriate because high availability failover keeps the same data state. Logical corruption is typically present on both primary and standby through synchronous replication, so failing over does not remove the corruption and does not reduce data loss.

Restore the most recent automated backup that was taken before the faulty release would likely cause unnecessary data loss because you would lose all transactions that occurred after that backup. You are not taking advantage of WAL archiving to restore to a more precise time just before the incident.

Use Database Migration Service to recreate the database from the last known good export and then resync changes is designed for migrations and not for rapid recovery from corruption.
