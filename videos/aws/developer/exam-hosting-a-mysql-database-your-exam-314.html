The correct option is Apply Cloud SQL rightsizing recommendations to tune CPU and memory based on recent utilization patterns. This aligns capacity with observed demand so you can maintain steady response times during bursts while avoiding unnecessary monthly spend.

Cloud SQL rightsizing uses recent utilization metrics to recommend an instance configuration that matches your workload. By adjusting CPU and memory based on actual peaks and sustained usage, you can keep latency consistent when promotions drive short spikes in connections and queries and still control costs during normal periods. You can schedule the change to minimize impact and you avoid overprovisioning for the entire month.

Enable autoscaling for compute resources on the Cloud SQL instance to expand and shrink capacity during traffic spikes is not viable because Cloud SQL does not support automatic scaling of CPU or memory. Cloud SQL offers automatic storage increase which does not help with transient compute spikes.

Create read replicas and route read traffic through a proxy so that the primary handles fewer queries during bursts is not the best fit because it only helps read heavy patterns and does nothing for writes. It also adds cost and replication lag risks, and Cloud SQL does not provide a proxy that automatically splits reads from writes for you.

Migrate the database to a multi-regional deployment so that peak load is distributed across multiple regions is not applicable because Cloud SQL instances are regional. You can use cross region replicas for reads and disaster recovery, yet there is no multi regional primary to distribute write load and this approach would increase cost without addressing short daily bursts effectively.
