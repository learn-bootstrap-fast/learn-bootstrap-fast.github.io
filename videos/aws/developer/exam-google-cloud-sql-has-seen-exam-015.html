The correct option is Analyze MySQL Performance Schema on the Cloud SQL instance to identify expensive statements and resource hot spots.

Using Performance Schema on Cloud SQL for MySQL gives immediate query level visibility into which statements are consuming the most time, waiting on locks, or doing excessive I O. You can quickly find the worst digests and their waits and then validate execution plans with EXPLAIN and take targeted actions such as adding a missing index or rewriting an inefficient query or terminating a runaway session. This approach addresses the root cause with minimal disruption because the analysis is read only and the remediation can be narrowly applied. Cloud SQL Query Insights for MySQL builds on Performance Schema and can further accelerate this investigation.

The option Introduce Memorystore in front of the database to cache frequent lookups and reduce pressure on MySQL is not an immediate fix and does not identify the query level cause. Integrating Memorystore requires application changes and cache warmup and it will not help with write heavy traffic or with problematic queries that miss the cache. Introducing a new component during an incident also increases risk.

The option Resize the Cloud SQL instance to a larger machine type to handle the spike in demand increases compute and memory but does not reveal which queries are slow or blocked. Changing the machine type triggers an instance restart which introduces disruption and it can mask inefficient queries or lock contention without resolving the underlying problem.

The option Create a read replica and route read traffic to it to lower utilization on the primary instance takes time to provision and backfill so it cannot relieve the issue quickly. It does not reduce write load and requires application routing changes and replica lag under heavy writes can complicate consistency.
