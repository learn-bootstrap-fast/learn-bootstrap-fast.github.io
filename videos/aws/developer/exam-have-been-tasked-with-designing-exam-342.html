The correct option is Configure Cloud Spanner regional replication and enable Point in Time Recovery for Cloud SQL for PostgreSQL.

For orders in Spanner, Cloud Spanner regional replication provides synchronous replicas across multiple zones in a region, which delivers near zero data loss for zonal outages and fast automatic failover well within the thirty minute restore time objective. It also keeps costs lower than a multi region deployment while still meeting the under five minute recovery point target for the most likely failure scenarios.

For user profiles in Cloud SQL, Point in Time Recovery for Cloud SQL for PostgreSQL continuously archives transaction logs so you can restore to a specific timestamp within the retention window. This supports an RPO of a few minutes and the service can create a new instance and apply logs in well under thirty minutes in typical environments, which satisfies both objectives while keeping ongoing costs reasonable.

Schedule daily exports of both databases to Cloud Storage using Storage Transfer Service is not sufficient because daily exports leave you with an RPO of up to twenty four hours and the orchestrator named is not how you initiate database exports from these services. Restores from exports also tend to exceed a thirty minute target.

Turn on automated backups for both services and store them in a Coldline bucket is incorrect because Cloud Spanner backups are a managed feature that you do not store in your own bucket or choose a storage class for, and daily automated backups alone do not meet an under five minute RPO. Coldline would not help restore speed and is not applicable to Spanner backups.

Enable Point in Time Recovery on Cloud SQL and create manual Cloud Spanner backups twice per day misses the RPO for Spanner because twice daily backups can lose up to twelve hours of data, and a restore from backups risks overshooting the thirty minute RTO.
