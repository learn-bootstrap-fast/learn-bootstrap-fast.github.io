The correct option is Create a Cloud SQL for MySQL instance in us-central1 with high availability enabled and add a cross region read replica in us-east1.

High availability on Cloud SQL keeps a standby in a different zone within the same region and it provides automatic failover during a zone outage. Adding a cross region read replica in us-east1 provides disaster recovery if the entire primary region fails. In that event you can promote the replica to restore write capability in the recovery region which satisfies both the local availability and regional recovery requirements.

Provision a single zone Cloud SQL for MySQL instance in us-central1-a and create a read replica in us-central1-b is incorrect because a single zone primary cannot survive a zone outage and a read replica is read only and does not provide automatic failover. Both instances are still in the same region so a regional failure would take them both down.

Build two independent HA instances by enabling high availability in both us-central1 and us-west1 and configure external replication between them is incorrect because this creates two primaries which is not a supported active active pattern on Cloud SQL and it removes managed failover. It also chooses us-west1 rather than the designated recovery region and adds unnecessary complexity compared to using a managed cross region read replica.

Migrate the workload to Cloud Spanner with multi region configuration is incorrect in this context because the requirement is to keep using Cloud SQL for MySQL. Spanner changes the database engine and application semantics and is not needed to meet the stated availability and disaster recovery goals.
