The correct choice is Build a custom migration that transforms MongoDB documents for Firestore using application code and Firestore APIs and use MongoDB change streams to keep Firestore in sync until cutover and maintain a temporary reverse copy process back to MongoDB for rollback.

This approach lets you implement the document model transformation explicitly in code so you can reshape collections, fields, and keys to match Firestore Native mode requirements. You can use Firestore client libraries along with high throughput patterns such as bulk writers to handle the 20 TB scale efficiently.

This plan also supports a short cutover window. You can run an initial bulk load, then consume MongoDB change streams to capture and apply ongoing changes to Firestore until the moment of cutover. That reduces downtime because only the final sync and validation need to happen during the 45 minute window. For rollback you can keep a temporary reverse copy path that mirrors writes from Firestore back to MongoDB during validation so if post migration checks fail you can redirect traffic to the still consistent source.
