The correct option is Run a Cloud SQL export that produces a SQL dump in Cloud Storage and import it into the target instance. This approach creates a consistent logical backup that captures both schema and data and you can restore it into a new staging instance within the required time window.

A SQL dump produced by Cloud SQL preserves database objects and metadata such as tables, indexes, sequences, constraints, and grants. The import then replays these statements to faithfully reconstruct the database in the target environment. The export runs from a consistent snapshot which provides transactional consistency across tables, and it is the Google recommended method for moving a full database between environments at this scale.

Use Cloud SQL export to write table data to CSV files in Cloud Storage and import them into a new instance is incorrect because CSV files contain only raw table rows and do not include schema, indexes, sequences, or foreign keys. You would need to recreate the schema and constraints manually and cross table consistency is not guaranteed in a single snapshot, which does not meet the requirement for a complete and consistent copy.

Create a read replica of the production instance in the same project and promote it to a standalone instance for staging is incorrect because read replicas are intended for read scaling and disaster recovery rather than environment cloning. Replicas must live in the same project and region constraints apply, so this does not satisfy a separate staging environment in many cases. Promotion also introduces operational complexity and is not the recommended pattern for producing a one time consistent copy for testing.

Trigger a JSON export with Cloud Functions and load the files into the staging database is incorrect because Cloud SQL does not support JSON export for relational backups and JSON would not capture the database schema. This workflow would not provide a reliable, importable copy of the database.
