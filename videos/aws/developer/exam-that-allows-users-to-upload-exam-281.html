The correct choice is Firestore and Cloud Functions.

With Firestore you can create a lightweight job record for each uploaded clip and use document create events to kick off processing. Those events can trigger Cloud Functions that transcode to two bitrates extract three preview frames and apply the overlay. Cloud Functions scales automatically based on load and scales to zero when idle which minimizes cost. Storing job status in Firestore keeps coordination simple and the solution remains fully managed with very little operational work.

Bigtable and Cloud Functions is a poor fit because the database is built for very high throughput and low latency workloads that require significant planning and management and it does not provide simple document triggers for this event driven workflow. This increases cost and operational effort without helping this use case.

Cloud Spanner and Cloud Run adds unnecessary complexity and cost for a simple media pipeline. The database is an expensive globally consistent relational system and the container service would require you to build and operate containers and often add a separate queue to trigger work which increases management overhead compared with an event driven serverless function.

Firestore and Compute Engine requires you to provision and manage virtual machines and autoscaling which goes against the requirement for very little operational management. It also does not scale to zero so it is typically more expensive for bursty workloads.
