The correct option is Analyze and tune slow or long-running queries on the primary and reduce transaction duration so replicas can apply WAL quickly.

Cloud SQL read replicas apply write-ahead log records in order and they can only keep up if the primary is generating WAL at a rate that the replicas can receive and apply efficiently. A spike in writes combined with long-running analytical queries that hold transactions open means the replicas must wait to apply some changes which increases apply time and causes lag. Shortening transaction lifetimes and optimizing the slow reports reduces contention and speeds up WAL replay which lets the replicas catch up and remain current without rebuilding anything.

Increase max_wal_senders and wal_keep_size on the primary does not address the cause of lag. More WAL senders or a larger WAL retention window can help prevent replicas from needing a rebuild if they fall too far behind or lose WAL segments. However it does not make the replicas apply WAL any faster and it does not fix slow queries or long transactions that are blocking timely WAL apply.

Stop all active queries and rebuild every read replica is unnecessary and disruptive. Rebuilding replicas does not change the rate at which WAL is produced or applied and it does not correct the long-running queries that are creating the backlog. The lag would simply return after the rebuild once the same workload resumes.

Enable high availability on the primary instance improves resiliency and failover but it does not reduce asynchronous read replica lag. HA protects the primary with a standby yet read replicas still apply WAL independently and will continue to lag if workload and transaction patterns are not optimized.
