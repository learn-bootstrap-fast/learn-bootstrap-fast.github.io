The correct option is Configure the maximum pool size slightly higher than the application's peak concurrent connection demand.

Right sizing the maximum pool size with a small amount of headroom over measured peak concurrency lets the pooler absorb brief spikes without creating excessive queuing. It keeps connection reuse efficient and reduces churn while helping you stay within the database instance connection limits. This approach improves throughput and latency because the pool is large enough to avoid backlog yet not so large that it overwhelms the backend or wastes resources.

Cloud SQL for PostgreSQL enforces a finite connection limit. A slightly higher pool ceiling protects the database by avoiding oversubscription while leaving capacity for administrative connections and maintenance tasks. It also keeps memory and CPU overhead from the pooler under control which improves overall efficiency.

Set the minimum pool size equal to the maximum pool size is ineffective because it pins all connections open even when idle which wastes memory and can consume valuable database connection slots. It removes elasticity and can increase backend pressure during quiet periods.

Configure the maximum pool size below the application's expected concurrent connections forces requests to queue behind the pool which increases latency and risks timeouts under load. The pooler becomes the bottleneck rather than smoothing demand.

Disable connection eviction and schedule health checks to run very frequently reduces pool health and increases overhead. Eviction is needed to recycle stale or unhealthy connections and very frequent health checks add unnecessary work and do not replace a sound eviction policy.
